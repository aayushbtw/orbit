# Differences from pstack

Orbit copies pstack (`pstack/` in cursor/plugins) at commit e1cc031, the SHA that every `skills.json` entry pins except `playbook-orchestrate`, which keeps de8ee15 because upstream deleted the file ([Orchestrate](#orchestrate)). Every **pstack.** line quotes e1cc031, not newer upstream. A line that names de8ee15, the previous pin, quotes text that orbit kept after e1cc031 cut or rewrote it. For Claude Code tool and path mappings, orbit follows pstack's adapter, `pstack/docs/harness/claude-code.md`. For T3 Code, orbit adds its own adapter, `plugin/docs/harness/t3-code.md` ([T3 Code host](#t3-code-host)). On a design fork, check pstack first. Record each difference here with its reason.

In the **orbit.** lines, paths under `agents/`, `hooks/` and `skills/`, and `rules.md`, are relative to `plugin/`, the folder the plugin ships from. Other paths are relative to the repo root.

### Loading rules

- **pstack.** The user runs `/poteto-mode` per task, typed as `/pstack:poteto-mode` in Claude Code (`README.md`).
- **orbit.** Three SessionStart hooks print `rules.md` every session, split at `# Delegation` and `# Writing the reply` (`hooks/hooks.json`). The first line of `rules.md` sends a goal with no named skill through `/orbit:start`, and a go-ahead on a change Claude proposed outside a flow counts as a goal. Poteto-mode's Non-negotiables follow it. `agents/poteto-agent.md` reads `rules.md` itself.
- **Why.** Rules hold without the user remembering a command. No per-task command loads, so routing has to live in the rules. Claude Code caps each hook's stdout at 10,000 characters and replaces longer output with a file path and a preview of the first 2,000 characters (code.claude.com/docs/en/hooks, read 2026-11-17), so one hook would drop most of `rules.md`. Two hooks split at `# Code Quality` left the second part at 9,931 characters at 0.55.0, so the next rules edit would have crossed the cap with no error. The three parts print about 5,500, 6,800 and 7,500 characters, and `tests/hooks/session-start.test.sh` fails a part of 9,000 characters or more. `# Code Quality` is no longer a split point, because the text before it is over 9,400 characters. The parts arrive in the order the hooks finish. Subagents don't get the SessionStart output. A "go" after a question-and-answer exchange once edited the main checkout with no worktree and collided with another session (transcript audit, 2026-11-10), so a go-ahead now enters a flow and its Worktree gate.

### Orbit-written skills

- **pstack.** poteto-mode's `SKILL.md` holds Non-negotiables, Principles, Autonomy, Subagents, Writing the reply and the playbook index. It has no gates. de8ee15 also had a Comments section. pstack ships its own `correct`.
- **orbit.** `skills/start`, `skills/ship`, `skills/correct` and `skills/playbook/SKILL.md` are orbit's text, with no `skills.json` entry. The playbook `SKILL.md` holds the gates, Principles, Stack rules and the index. poteto-mode's other sections live in `rules.md`. `correct` keeps pstack's order (architecture, then a type or lint, then a test, then a doc) and its rule table, but handles one named mistake with one guard. It drops the class sweep, the exception rule and the **Reply:**.
- **Why.** `start` and `ship` are entry commands that pstack's single `/poteto-mode` doesn't need. The Worktree, Plan and Delegate gates are orbit's. `rules.md` loads every session, so the always-on sections go there. `correct`'s rewrite has no recorded reason.

### Trigger list

- **pstack.** e1cc031 cuts poteto-mode's Non-negotiables to ten short lines and adds one. "Starting any agent, whether a Task subagent or a Project worker → the first line of its kickoff is `Read <path>/worker.md before anything else.`" `worker.md` holds the operator's rules for every started agent, among them "The bar in your kickoff is the whole bar. Add no check, gate, sign-off or review round above it." (`poteto-mode/SKILL.md`, `poteto-mode/worker.md`)
- **orbit.** rules.md Non-negotiables keep the de8ee15 trigger list with orbit's edits, including "Nontrivial change, architecture decision, or "are we sure?" → `/orbit:how`." Orbit ships no `worker.md` and adds no kickoff line. Agents get the operator's rules through rules.md, `agents/poteto-agent.md` and the Delegate gate brief.
- **Why.** rules.md is orbit's counterpart of poteto-mode's triggers, and it carries orbit and T3 Code triggers that the short list lacks. The prod-ready program rewrites rules.md in a later unit (P5), which can port the shorter wording. `worker.md`'s "Add no check, gate, sign-off or review round above it" would cut orbit's [Plan gate](#plan-gate) and pre-land [Independent verifier](#independent-verifier) (P13 review, 2026-11-17).

### Worktree for the main chat

- **pstack.** "Work from a git worktree off trunk, and keep unrelated work out of it" (`playbooks/opening-a-pr.md`), with no tool named and no recovery steps. de8ee15 also had "Dirty branch with unrelated work: patch out, fresh worktree, apply. Snarled worktree: reset from main, redo minimally."
- **orbit.** The Worktree gate (`skills/playbook/SKILL.md`) calls `EnterWorktree` named `<type>-<slug>`, then runs `git branch -m <type>/<slug>`. It carries both de8ee15 recovery sentences, which e1cc031 cut, and they override its skip-when-in-a-worktree rule. "Reset from main" becomes a fresh worktree. Either case runs `ExitWorktree` with `keep` first. Shipping step 7 removes a task's worktree and branch once it lands, and `/orbit:worktree-cleanup` prunes abandoned ones ([Shipping](#shipping)).
- **Why.** Claude Code's worktree tools. gitops never runs `reset --hard` (`agents/gitops.md`). `EnterWorktree` names the branch `worktree-<name>`, so the gate renames it. Opening a PR pushes `<type>/<slug>`, and the worktree-cleanup audit matches PRs by local branch name.

### Worktree setup

- **pstack.** No setup step.
- **orbit.** Before entering, if `git check-ignore -q .claude/worktrees` fails, the Worktree gate appends `.claude/worktrees` to `.git/info/exclude`. After entering, it runs `vp install` when the project has a lockfile. Gitignored files the Check needs, such as `.env*` or `.claude/settings.local.json`, come in through the project's `.worktreeinclude`, which Claude Code copies into each new worktree. When one is missing, the gate adds its pattern there and copies the file in once.
- **Why.** Orbit's choice. `EnterWorktree` puts worktrees under `.claude/worktrees`, so the exclude keeps them out of the main checkout's `git status` without a tracked `.gitignore` edit. A fresh worktree has no installed dependencies, so the Check line can't run without the install. It also has no gitignored files, and agents copied `.env.local` in by hand in 4 sessions (transcript audit, 2026-11-10). `.worktreeinclude` makes the copy happen once per project instead of once per worktree.

### Plan gate

- **pstack.** No plan gate and no advisor. pstack ships only `poteto-agent` and `comment-sicko` (`agents/`).
- **orbit.** The Plan gate (`skills/playbook/SKILL.md`) runs when a change adds a module or touches more than 3 files. The lead reads the project sources for those paths, briefs `orbit:advisor` (`agents/advisor.md`, Fable at `high` unless the project's `advisor` row changes it, read-only) with the plan and the sources, and acts on its verdict. If the spawn fails because Fable is unavailable or its usage limit is reached, the lead retries once on Opus (rules.md Workflow Defaults, Models). The advisor has no T3 Code tools, because it only reads and returns a verdict.
- **Why.** Orbit's choice. A second model checks a multi-file plan against the project's rules before code exists, when a wrong shape costs least to fix. The advisor moved from Opus to Fable on 2026-11-10. Anthropic's Fable 5.2 launch page (https://www.anthropic.com/claude-fable-and-mythos-5-2) names Fable for the advisor role, where "Haiku, Sonnet, or Opus models consult it". The same page recommends Opus as the daily driver, so under the defaults the lead runs on Opus and a Fable advisor is a second model.

### Running another skill

- **pstack.** "`Read` `<pstack>/skills/<name>/SKILL.md` and follow it. The `Skill` tool refuses most pstack skills." (`docs/harness/claude-code.md`)
- **orbit.** The Skill tool runs `start`, `playbook`, `ship`, `how`, `why`, `architect`, `arena`, `interrogate`, `swarm`, `figure-it-out`, `deslop`, `no-comments`, `unslop`, `technical-writing`, `control-ui`, `control-cli`, `pause-safely`, `worktree-cleanup` and `rules`. Flows read the principle leaves, `tdd`, `benchmark-checklist`, `show-me-your-work`, `ketchup` and `typescript-best-practices` by path. `rules.md` gives `benchmark-checklist` and `show-me-your-work` the bundled path, `<orbit-plugin>/skills/<name>/SKILL.md`. It gives `bugbot-triage.md` the bundled path `<orbit-plugin>/skills/playbook/references/bugbot-triage.md`. Skill bodies give a bundled path relative to the skill's own directory, such as `../arena/SKILL.md`. `setup`, `correct`, `recall`, `reflect`, `automate-me`, `session-pickup`, `create-verification-skill` and `maintain-verification-skill` keep `disable-model-invocation`, so the user types them.
- **Why.** `${CLAUDE_SKILL_DIR}` expands only in a skill that the Skill tool loads or the user types. `playbook` and `worktree-cleanup` find their files through it. Flows also pass `$ARGUMENTS`, which a Read by path can't. The SessionStart hooks print `rules.md` through `sed`, which rewrites `<orbit-plugin>` to the plugin root. Grok loads the plugin but drops the SessionStart output and leaves `${CLAUDE_PLUGIN_ROOT}` unexpanded in skill bodies. It gives the model each skill's base directory, so a relative path resolves there, and a lead without the hook output loads the `rules` skill, which reads `../../rules.md`. Agents keep `${CLAUDE_PLUGIN_ROOT}`, which Claude Code and Grok expand in agent bodies.
Codex loads no agent, so the brief maps the variable ([Lead on another provider](#lead-on-another-provider)).

### T3 Code host

- **pstack.** pstack's Claude Code adapter (`pstack/docs/harness/claude-code.md`) maps Cursor names to Claude Code. Its Cursor-only features section skips what Claude Code lacks. "Claude Code has no Cursor Automations, Bugbot, Cursor cloud agents, or built-in PR tool. When a step needs one, put one line in your reply, `Skipped in Claude Code: <step>. <reason>.`, then go on to the next step."
- **orbit.** `plugin/docs/harness/t3-code.md` maps pstack's names to T3 Code in three columns, pstack, T3 Code and T3 tool absent. It sits under `docs/harness/`, the folder pstack uses for a host adapter. Before calling a T3 tool, each agent checks that tool itself. The tool is present when it is in the agent's tool list, or when `ToolSearch` with `select:mcp__t3-code__<name>` loads it. With no `ToolSearch`, a tool not in the list is absent. T3 tools may load late, so the agent tries a missing tool's name once, by `ToolSearch` `select:` or else by its first real call, before it calls the tool absent. The probe has no families and never keys on another tool of the same family. Any `mcp__t3-code__` tool in the list tells the agent the host is T3, never that another tool is present. A tool that is not present takes the absent column. The rows map `Task`, `environment: "cloud"`, Cursor Automations, `SendToUser` secret requests, a built-in PR tool, a wait on a PR event and background work the agent waits on. The Automations row adds that a request only to schedule calls `schedule_task` and does not run its prompt now. The secrets row adds the sudo flow, a `delivery: "file"` secret fed to `sudo -S -p '' <cmd>` on stdin, with any other input as a file argument. Seven rows are orbit's own, since pstack's adapter has none of them. They are `/loop`, a question about a T3 thread by its id, a browser step the user asked for, a lead in T3 plan mode, gitops's CI wait, a verdict's proof table and the user's Stop. `/loop` maps to `schedule_task` bound to the thread when that tool is present. A question about a thread runs `t3_thread_read` on it before the answer, and without that tool the agent says it cannot read the thread and writes no skip line. A verdict's proof table goes through `html_preview` with an HTML file path or inline HTML, then `html_render`, when both are present, else into an in-chat table, as swarm Phase D's result table. A chart for a trend or comparison, such as ketchup's, takes the same row, else a Mermaid chart ([ketchup](#ketchup)). The built-in PR tool row links each PR gitops creates, takes over or pushes to, with `link_pull_requests` for several, and says when linking fails. The PR wait is two rows. gitops asked to wait on CI runs the watcher once with `--once` on every host and reports the verdict ([gitops agent](#gitops-agent)). The lead's own wait follows babysit's **Host watcher** ([Babysit](#babysit)). In T3 it reads once with `--once`, calls `watch_pull_request` on a pending `TIMEOUT`, ends the turn, and unwatches before a handback. In T3 with that tool off it reads once per turn and hands back. Outside T3 it runs the bare watcher under `/loop`. Bugbot and Cursor cloud agents keep the adapter's rows in both columns. Paths is one sentence, because T3 changes no path. Models keeps rules.md's Claude mapping and adds a row for a non-Claude slug, a panel seat on another family, with a Seats on another family section ([Seats on another family](#seats-on-another-family)). The lead calls `orchestrator_capabilities` once per thread, and again only after an error or a user-named provider change, or with `search` for a model the Models table names. The session's family is the `driverKind` of the provider whose `providerInstanceId` equals `inheritedProviderInstanceId`. The roster is every provider, in listed order, with `canRunCrossProviderChildTask` true, a non-empty `models` list and another `driverKind`. The session's own provider never joins the roster. When no provider matches `inheritedProviderInstanceId`, the reply says so and the session-family seat runs. The session-family seat is the seat the skill names, run on the session's own family, an `Agent` spawn under a Claude lead and the native subagent under another lead. The `other-family` row picks the seat ([Model per role](#model-per-role)), and its Effort maps onto the model's own option id. Its empty-cell default takes the first roster provider's first model whose `id` does not start with the first word of `inheritedModel`, and moves to the next provider when one has none. `auto` and `default` stay eligible, and the reply names them. A list in the row tries only its entries outside the session's family, in list order, then the session-family seat, and never a provider it leaves out. Before the lead calls an explicit pick unavailable because its model is not listed, it calls `orchestrator_capabilities` with `search` set to the model id. The lead spawns the seat with `delegate_task`, ends the turn, reads the result with `task_status` when the child's completion wakes it, and settles the child thread. Each spawn carries a `clientRequestId` naming the skill, the seat and the round, reused on a retry of the same call and new for a new round or a fallback. A seat or child that runs commands skips a provider whose listed `runtimeModes` lacks the parent's runtime mode. A child's question goes through `t3_pending_request` on its `childThreadId`, answered from the brief's context or else by the user, and `archive` is only for a child the lead abandons or when that tool is absent. A failed seat moves to the next list entry, or with no list the next roster provider, then to the session-family seat. An empty or fully failed roster runs the session-family seat, and the reply says the panel lacked a second family. In the absent column the session-family seat runs, and the reply names each seat's model. "Roster" has no pstack name. pstack says "family", which arena Phase A step 3 defines by slug prefix, and "pool", as in `arena cross-judge pool`. Read-only and shared-checkout children stay foreground `Agent` calls. Under a T3 lead with `delegate_task`, a child that needs its own checkout or runs while the lead keeps working, such as a parallel delegate, the native verifier or an autopilot owner's build round, is a same-provider `delegate_task` child, and a panel seat on another family is a cross-provider one ([Own-checkout children](#own-checkout-children)). Each `Agent` call passes `run_in_background: false`, and parallel spawns go as several calls in one message ([Agent call defaults](#agent-call-defaults)). A new round's brief carries the original brief, the prior round's findings, the responses to them and the objections still open. A skipped step gets the line `Skipped outside T3: <step>. <reason>.` The built-in PR tool row's absent column is `gh pr create` and writes no line, as pstack's adapter says, "That is not a skip, so write no line." rules.md Delegation points at the file once, in **Host tools.**
Under a Codex lead it looks for a tool under both `t3-code` and `t3-code-direct`. The one exception to the probe is a session connected to T3 from outside. When a call there returns the error that the tool needs an agent running inside T3 Code, that tool and the rest of the tools that act as the calling thread take the absent column, and `t3_thread_launch` never stands in for them unless the user asked for a new thread.
A verifier whose `verifier` row reads `other-family` runs as a seat on another family through `delegate_task` ([Independent verifier](#independent-verifier)). The native verifier runs as a same-provider child ([Own-checkout children](#own-checkout-children)).
A browser step the user asked for runs `preview_status` first, then `preview_open` only if no tab can be automated, and closes a tab it opened with `t3_preview_close` before the reply, unless the user asked for it or uses it. No agent uses `preview_*` unasked to verify or show its own edit. Without the tools, the step runs on the control-ui harness. A lead in T3 plan mode reads its mode from `orchestrator_capabilities` and passes `interactionMode: "plan"` on every `delegate_task`, never `"default"`, and omits the field when unsure. A native child's brief carries T3's plan-mode rule verbatim, and the lead spawns no code writer in plan mode. The user's Stop ends the thread's PR watches and stops its delegated tasks. Nothing re-arms on its own, and resumed PR work goes back through the lead's PR wait row ([Playbooks as skills](#playbooks-as-skills)). The read trigger in the adapter's opening names the browser step and a child in plan mode.
- **Why.** T3 Code has a tool for three of the adapter's rows. `schedule_task` covers Automations, `request_secret` covers secret requests, and `link_pull_request` follows `gh pr create` for the built-in PR tool. T3's runtime rule for every thread (`runtimeInstructions.ts` line 3 in pingdotgg/t3code at c2eb8f3) says "Link each PR you create, take over, or push to: link_pull_request, or link_pull_requests for several, full URL, every stack layer, as your next call. The old row's "A later push to a linked PR needs no new link." contradicted "push to", and `link_pull_request` is idempotent (`Tool.Idempotent` in T3's `pr-tools.ts`), so a repeat link costs nothing. The same line sets the PR wait, quoted under [Babysit](#babysit). Bugbot and cloud agents have no T3 tool, so their rows match the adapter's. A probe beats an environment variable, because T3 can turn a tool off inside a T3 session and the variable says nothing about which (T3-native plan, rejected alternatives, 2026-11-16). The probe checks each tool, not one per family, because T3 can turn one tool off and leave the rest of its family on (inferred). pstack keeps its host adapter at `docs/harness/claude-code.md`, so orbit's T3 adapter takes the same folder under `plugin/`. The T3-native plan renders each verdict's proof table in the coordinator thread with `html_render`, and swarm Phase D already returns its result table in chat, which covers a session without the tool. The threads cluttered the sidebar, needed settling by hand, and died in a T3 restart as a subagent would (T3-native plan, rejected alternatives). The skip line says "outside T3" because an absent tool can also mean a T3 session with that tool off (inferred). The PR row once had the lead write `Skipped outside T3: link PR.`, and under `claude -p` with no T3 the reply carried it on every PR (interrogate, 2026-11-16). The probe lane on 2026-11-16 also saw `/loop` with no interval schedule its wake with `ScheduleWakeup`, as the `/loop` row says. pstack's adapter maps a non-Claude slug as "Omit `model` so the agent runs on the session model, and say so." Orbit's absent column departs from that line. ### Lead on another provider

- **pstack.** pstack's text uses Cursor names, and its one adapter, `pstack/docs/harness/claude-code.md`, maps them for Claude Code. It has no adapter for a lead on another provider and no mapping from Claude Code names.
- **orbit.** `plugin/docs/harness/t3-code.md` adds a section, Lead on another provider, after Probe. It is one table, Claude Code to lead on another provider, in the two-column shape of pstack's Claude Code adapter. `Agent` with an `orbit:` agent maps to the provider's native subagent tool, such as Grok's `spawn_subagent`, else `delegate_task`. Every orbit agent runs this way, code writers included, and no code child moves to another provider. Beside the no-native-tool case, `delegate_task` fills a panel seat on another family, the verifier seat, and a same-provider child that needs its own checkout or runs while the lead keeps working. Every brief names orbit's plugin folder as an absolute path. `mcp__t3-code__<name>` maps to the bare name the tool list shows, and under a Codex lead `delegate_task` and `t3_thread_wait` sit on `t3-code-direct`. The lead's own tool search, such as Grok's `search_tool`, takes the place of `ToolSearch`. With none, a tool in the list is present, else the first real call probes it, never a dummy call. The agent file's `model` field does not apply, and the reply names the model each spawn ran on. Every spawn runs on the lead's own model, and a Models cell that names a Claude model is skipped, while `inherit` and Effort cells still apply. The effort goes in the native tool's effort field when it has one, such as Codex's `reasoning_effort`, else the lead omits it and says so. A model-invocable pause-safely runs on "pause" or before compaction. rules.md Files puts working notes in auto memory, not the repo, so only the folder differs from pstack. Orbit once wrote one shared `resume.md`, and a pause in another session overwrote it ("the resume.md was overwritten what work do we have left here?", transcript audit, 2026-11-10).
T3's runtime prompt says "Before handback, call unwatch_pull_request on any PR you watch." and "Call watch_pull_request when asked to monitor or babysit, or when work you were asked to do, such as a merge, still waits on checks or reviews, even after an earlier unwatch." Babysit already waits on the PR per **Host watcher**, so pickup routes there instead of arming its own. `list_thread_pull_requests` takes "Thread. Default: this thread." (`pr-tools.ts:313` in pingdotgg/t3code at c2eb8f3), and pickup runs in a new session, so a call with no `threadId` finds none of the prior thread's PRs.
