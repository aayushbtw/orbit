# Differences from pstack

Orbit copies pstack (`pstack/` in cursor/plugins) at commit de8ee15, the SHA that every `skills.json` entry pins. Every **pstack.** line quotes de8ee15, not newer upstream. For Claude Code tool and path mappings, orbit follows pstack's adapter, `pstack/docs/harness/claude-code.md`. For T3 Code, orbit adds its own adapter, `plugin/docs/harness/t3-code.md` ([T3 Code host](#t3-code-host)). On a design fork, check pstack first. Record each difference here with its reason.

In the **orbit.** lines, paths under `agents/`, `hooks/` and `skills/`, and `rules.md`, are relative to `plugin/`, the folder the plugin ships from. Other paths are relative to the repo root.

### Loading rules

- **pstack.** The user runs `/poteto-mode` per task, typed as `/pstack:poteto-mode` in Claude Code (`README.md`).
- **orbit.** Two SessionStart hooks print `rules.md` every session, split at `# Code Quality` (`hooks/hooks.json`). The first line of `rules.md` sends a goal with no named skill through `/orbit:start`, and a go-ahead on a change Claude proposed outside a flow counts as a goal. Poteto-mode's Non-negotiables follow it. `agents/poteto-agent.md` reads `rules.md` itself.
- **Why.** Rules hold without the user remembering a command. No per-task command loads, so routing has to live in the rules. Claude Code inlines about 10 KB per hook and shows only a 2 KB preview past that, so one hook would drop the end of `rules.md`. The two parts arrive in the order the hooks finish. Subagents don't get the SessionStart output. A "go" after a question-and-answer exchange once edited the main checkout with no worktree and collided with another session (transcript audit, 2026-11-10), so a go-ahead now enters a flow and its Worktree gate.

### Orbit-written skills

- **pstack.** poteto-mode's `SKILL.md` holds Non-negotiables, Principles, Autonomy, Subagents, Writing the reply, Comments and the playbook index. It has no gates. pstack ships its own `correct`.
- **orbit.** `skills/start`, `skills/ship`, `skills/correct` and `skills/playbook/SKILL.md` are orbit's text, with no `skills.json` entry. The playbook `SKILL.md` holds the gates, Principles, Stack rules and the index. poteto-mode's other sections live in `rules.md`. `correct` keeps pstack's order (architecture, then a type or lint, then a test, then a doc) and its rule table, but handles one named mistake with one guard. It drops the class sweep, the exception rule and the **Reply:**.
- **Why.** `start` and `ship` are entry commands that pstack's single `/poteto-mode` doesn't need. The Worktree, Plan and Delegate gates are orbit's. `rules.md` loads every session, so the always-on sections go there. `correct`'s rewrite has no recorded reason.

### Worktree for the main chat

- **pstack.** "Work from a git worktree off main", with no tool named. "Dirty branch with unrelated work: patch out, fresh worktree, apply. Snarled worktree: reset from main, redo minimally." (`playbooks/opening-a-pr.md`)
- **orbit.** The Worktree gate (`skills/playbook/SKILL.md`) calls `EnterWorktree` named `<type>-<slug>`, then runs `git branch -m <type>/<slug>`. It carries both recovery sentences, and they override its skip-when-in-a-worktree rule. "Reset from main" becomes a fresh worktree. Either case runs `ExitWorktree` with `keep` first. Shipping step 7 removes a task's worktree and branch once it lands, and `/orbit:worktree-cleanup` prunes abandoned ones ([Shipping](#shipping)).
- **Why.** Claude Code's worktree tools. gitops never runs `reset --hard` (`agents/gitops.md`). `EnterWorktree` names the branch `worktree-<name>`, so the gate renames it. Opening a PR pushes `<type>/<slug>`, and the worktree-cleanup audit matches PRs by local branch name.

### Worktree setup

- **pstack.** No setup step.
- **orbit.** Before entering, if `git check-ignore -q .claude/worktrees` fails, the Worktree gate appends `.claude/worktrees` to `.git/info/exclude`. After entering, it runs `vp install` when the project has a lockfile. Gitignored files the Check needs, such as `.env*` or `.claude/settings.local.json`, come in through the project's `.worktreeinclude`, which Claude Code copies into each new worktree. When one is missing, the gate adds its pattern there and copies the file in once.
- **Why.** Orbit's choice. `EnterWorktree` puts worktrees under `.claude/worktrees`, so the exclude keeps them out of the main checkout's `git status` without a tracked `.gitignore` edit. A fresh worktree has no installed dependencies, so the Check line can't run without the install. It also has no gitignored files, and agents copied `.env.local` in by hand in 4 sessions (transcript audit, 2026-11-10). `.worktreeinclude` makes the copy happen once per project instead of once per worktree.

### Plan gate

- **pstack.** No plan gate and no advisor. pstack ships only `poteto-agent` and `comment-sicko` (`agents/`).
- **orbit.** The Plan gate (`skills/playbook/SKILL.md`) runs when a change adds a module or touches more than 3 files. The lead reads the project sources for those paths, briefs `orbit:advisor` (`agents/advisor.md`, Fable at `high` unless the project's `advisor` row changes it, read-only) with the plan and the sources, and acts on its verdict. If the spawn fails because Fable is unavailable or its usage limit is reached, the lead retries once on Opus (rules.md Workflow Defaults, Models). The advisor has no T3 Code tools, because it only reads and returns a verdict.
- **Why.** Orbit's choice. A second model checks a multi-file plan against the project's rules before code exists, when a wrong shape costs least to fix. The advisor moved from Opus to Fable on 2026-11-10. Anthropic's Fable 5.2 launch page (https://www.anthropic.com/claude-fable-and-mythos-5-2) names Fable for the advisor role, where "Haiku, Sonnet, or Opus models consult it". The same page recommends Opus as the daily driver, so under the defaults the lead runs on Opus and a Fable advisor is a second model.

### Running another skill

- **pstack.** "`Read` `<pstack>/skills/<name>/SKILL.md` and follow it. The `Skill` tool refuses most pstack skills." (`docs/harness/claude-code.md`)
- **orbit.** The Skill tool runs `start`, `playbook`, `ship`, `how`, `why`, `architect`, `arena`, `interrogate`, `swarm`, `figure-it-out`, `deslop`, `no-comments`, `unslop`, `technical-writing`, `control-ui`, `control-cli`, `pause-safely`, `worktree-cleanup` and `rules`. Flows read the principle leaves, `tdd`, `benchmark-checklist`, `show-me-your-work`, `ketchup` and `typescript-best-practices` by path. `rules.md` gives `benchmark-checklist` and `show-me-your-work` the bundled path, `<orbit-plugin>/skills/<name>/SKILL.md`. It gives `bugbot-triage.md` the bundled path `<orbit-plugin>/skills/playbook/references/bugbot-triage.md`. Skill bodies give a bundled path relative to the skill's own directory, such as `../arena/SKILL.md`. `setup`, `correct`, `recall`, `reflect`, `automate-me`, `session-pickup`, `create-verification-skill` and `maintain-verification-skill` keep `disable-model-invocation`, so the user types them.
- **Why.** `${CLAUDE_SKILL_DIR}` expands only in a skill that the Skill tool loads or the user types. `playbook`, `how`, `why`, `architect` and `worktree-cleanup` find their files through it. Flows also pass `$ARGUMENTS`, which a Read by path can't. The SessionStart hooks print `rules.md` through `sed`, which rewrites `<orbit-plugin>` to the plugin root. Grok loads the plugin but drops the SessionStart output and leaves `${CLAUDE_PLUGIN_ROOT}` unexpanded in skill bodies. It gives the model each skill's base directory, so a relative path resolves there, and a lead without the hook output loads the `rules` skill, which reads `../../rules.md`. Agents keep `${CLAUDE_PLUGIN_ROOT}`, which Claude Code and Grok expand in agent bodies.

### T3 Code host

- **pstack.** pstack's Claude Code adapter (`pstack/docs/harness/claude-code.md`) maps Cursor names to Claude Code. Its Cursor-only features section skips what Claude Code lacks. "Claude Code has no Cursor Automations, Bugbot, Cursor cloud agents, or built-in PR tool. When a step needs one, put one line in your reply, `Skipped in Claude Code: <step>. <reason>.`, then go on to the next step."
- **orbit.** `plugin/docs/harness/t3-code.md` maps pstack's names to T3 Code in three columns, pstack, T3 Code and T3 tool absent. It sits under `docs/harness/`, the folder pstack uses for a host adapter. Before calling a T3 tool, each agent checks that tool itself. The tool is present when it is in the agent's tool list, or when `ToolSearch` with `select:mcp__t3-code__<name>` loads it. With no `ToolSearch`, a tool not in the list is absent. The probe has no families and never keys on another tool of the same family. A tool that is not present takes the absent column. The rows map `Task`, `environment: "cloud"`, Cursor Automations, `SendToUser` secret requests, a built-in PR tool, a wait on a PR event and background work the agent waits on. Three rows are orbit's own, since pstack's adapter has none of them. They are `/loop`, gitops's CI wait and a verdict's proof table. `/loop` maps to `schedule_task` bound to the thread when that tool is present. A verdict's proof table goes through `html_render` when that tool is present, else into an in-chat table, as swarm Phase D's result table. The PR wait is two rows. gitops asked to wait on CI runs the watcher once with `--timeout 120` on every host and hands a `TIMEOUT` to its lead ([gitops agent](#gitops-agent)). The lead's own wait runs the watcher with `--timeout 120` and, on a `TIMEOUT` with reason `pending-checks`, arms `watch_pull_request` when that tool is present. When it is absent, the lead runs the bare watcher under `/loop`, per babysit step 6 ([Babysit](#babysit)). Bugbot and Cursor cloud agents keep the adapter's rows in both columns. Paths is one sentence, because T3 changes no path. Models keeps rules.md's Claude mapping and adds a row for a non-Claude slug, a panel seat on another family, with a Seats on another family section ([Seats on another family](#seats-on-another-family)). The lead calls `orchestrator_capabilities` once per session. The session's family is the `driverKind` of the provider whose `providerInstanceId` equals `inheritedProviderInstanceId`. The roster is every provider, in listed order, with `canRunCrossProviderChildTask` true, a non-empty `models` list and another `driverKind`. The session's own provider never joins the roster. When no provider matches `inheritedProviderInstanceId`, the reply says so and the session-family seat runs. The session-family seat is the seat the skill names, run on the session's own family, an `Agent` spawn under a Claude lead and the native subagent under another lead. The `other-family` row picks the seat ([Model per role](#model-per-role)), and its Effort maps onto the model's own option id. Its empty-cell default takes the first roster provider's first model whose `id` does not start with the first word of `inheritedModel`, and moves to the next provider when one has none. `auto` and `default` stay eligible, and the reply names them. A list in the row tries only its entries outside the session's family, in list order, then the session-family seat, and never a provider it leaves out. Before the lead calls an explicit pick unavailable because its model is not listed, it calls `orchestrator_capabilities` with `search` set to the model id. The lead spawns the seat with `delegate_task`, ends the turn, reads the result with `task_status` when the child's completion wakes it, and settles the child thread. A failed seat moves to the next list entry, or with no list the next roster provider, then to the session-family seat. An empty or fully failed roster runs the session-family seat, and the reply says the panel lacked a second family. In the absent column the session-family seat runs, and the reply names each seat's model. "Roster" has no pstack name. pstack says "family", which arena Phase A step 3 defines by slug prefix, and "pool", as in `arena cross-judge pool`. Subagents, owners, verifiers, swarm workers and live lanes stay `Agent` calls, and `delegate_task` is only for a panel seat on another family. A skipped step gets the line `Skipped outside T3: <step>. <reason>.` The built-in PR tool row's absent column is `gh pr create` and writes no line, as pstack's adapter says, "That is not a skip, so write no line." rules.md Delegation points at the file once, in **Host tools.**
- **Why.** T3 Code has a tool for three of the adapter's rows. `schedule_task` covers Automations, `request_secret` covers secret requests, and `link_pull_request` follows `gh pr create` for the built-in PR tool. Bugbot and cloud agents have no T3 tool, so their rows match the adapter's. A probe beats an environment variable, because T3 can turn a tool off inside a T3 session and the variable says nothing about which (T3-native plan, rejected alternatives, 2026-11-16). The probe checks each tool, not one per family, because T3 can turn one tool off and leave the rest of its family on (inferred). pstack keeps its host adapter at `docs/harness/claude-code.md`, so orbit's T3 adapter takes the same folder under `plugin/`. The T3-native plan renders each verdict's proof table in the coordinator thread with `html_render`, and swarm Phase D already returns its result table in chat, which covers a session without the tool. Being in T3 also doesn't give every agent the tools. An `orbit:verifier` saw none until its `tools` frontmatter named them (T3 probe lane, 2026-11-16), so each agent probes for itself. Owners, verifiers and swarm workers once ran as `delegate_task` child threads. The threads cluttered the sidebar, needed settling by hand, and died in a T3 restart as a subagent would (T3-native plan, rejected alternatives). `Agent` already gives a worktree, parallel runs and fresh context. pstack ships a Claude Code adapter beside its Cursor-native text, so the absent column keeps orbit working in plain Claude Code and in a T3 session with a tool turned off. The skip line says "outside T3" because an absent tool can also mean a T3 session with that tool off (inferred). The PR row once had the lead write `Skipped outside T3: link PR.`, and under `claude -p` with no T3 the reply carried it on every PR (interrogate, 2026-11-16). The probe lane on 2026-11-16 also saw `/loop` with no interval schedule its wake with `ScheduleWakeup`, as the `/loop` row says. pstack's adapter maps a non-Claude slug as "Omit `model` so the agent runs on the session model, and say so." Orbit's absent column departs from that line. Each skill's Claude seat already is the session-family seat orbit runs without T3, and a caveat on every non-T3 run is noise (advisor plan gate, 2026-11-16). Orbit keys family on `driverKind` because the capabilities result carries no family field, and `driverKind` is its only per-provider kind (inferred). A provider of another `driverKind` can still list a Claude model, and some list a model named `default`, so an explicit `other-family` pick is the fix (advisor, 2026-11-16). `t3_background_wait` refuses `delegate_task` ids ("Subagent, Agent tool, and delegate_task IDs don't go here.", T3-3 probe, 2026-11-16), so the lead ends the turn and the child's completion wakes it. An aggregator provider of another `driverKind` can host a model of the session's own family, so the empty-cell default skips a model whose `id` starts with the session model's first word (advisor, 2026-11-16). `orchestrator_capabilities` returns a short list and takes `search`, so a model missing from the first result can still be in the catalog. The skill's Claude seat became the session-family seat because the lead need not be Claude.

### Lead on another provider

- **pstack.** pstack's text uses Cursor names, and its one adapter, `pstack/docs/harness/claude-code.md`, maps them for Claude Code. It has no adapter for a lead on another provider and no mapping from Claude Code names.
- **orbit.** `plugin/docs/harness/t3-code.md` adds a section, Lead on another provider, after Probe. It is one table, Claude Code to lead on another provider, in the two-column shape of pstack's Claude Code adapter. `Agent` with an `orbit:` agent maps to the provider's native subagent tool, such as Grok's `spawn_subagent`, else `delegate_task`. A child that writes code runs on the roster's Claude provider through `delegate_task`, because only a child on Claude gets the role's model and orbit's rules. It runs native with a line in the reply when a T3 tool is absent, the roster has no Claude provider, or the spawn errors or returns nothing. The lead reads its result with `task_status` and settles its thread as a panel seat's. Every brief names orbit's plugin folder as an absolute path. `mcp__t3-code__<name>` maps to the bare name the tool list shows. The lead's own tool search, such as Grok's `search_tool`, takes the place of `ToolSearch`. With none, a tool in the list is present, else the first real call probes it, never a dummy call. The agent file's `model` field does not apply, and the reply names the model each spawn ran on. Background work, `AskUserQuestion`, worktrees and the SessionStart rules map to the native tool, the native question tool or else a numbered question, the native worktree option and the `rules` skill. Any other Claude-only tool takes its native equivalent, else the skip line. The `rules` skill sends a lead that is not Claude Code to this section ([Running another skill](#running-another-skill)).
- **Why.** The user's direction is to run orbit in T3 Code under any provider that can lead a thread. Grok sees T3 tools as `t3-code__<name>`, finds them with `search_tool` and calls them with `use_tool`, asks with `ask_user_question`, and ignores an agent's `model` frontmatter (T3-4 evidence, 2026-11-16). Its native subagents take `subagent_type` with orbit's agents and show as nested nodes in T3, so they start no top-level thread, which the user avoids. A `delegate_task` child loads orbit's rules and skills only when it runs on Claude, so code stays on Claude when the roster has it. Grok expands `${CLAUDE_PLUGIN_ROOT}` in agent bodies but not in skill bodies, and another provider may expand neither, so a brief names the plugin folder. A dummy `delegate_task` would start a real thread, so the probe is the first real call.

### Commits

- **pstack.** No actor named. "Commit liberally" (`playbooks/feature.md` step 4). "Rebase into small, ordered commits" (`feature.md` step 6, `opening-a-pr.md`). Bodies follow `/technical-writing`.
- **orbit.** The parent reviews each unit, then `orbit:gitops` commits it by path, with a subject and a body that says why, under `technical-writing` (`agents/gitops.md`). Unpushed fixes fold in with fixup and autosquash. Feature step 6 and refactoring step 8 keep pstack's rebase into small, ordered commits. gitops runs it before Shipping, with fixup and autosquash on unpushed units, and never rewrites a pushed commit. Refactor commits land in step 8's order, and bug's failing repro is its own unit before the fix.
- **Why.** Review comes before commit, and git output stays out of the main context. Orbit once dropped the rebase step on the grounds that units committed in order leave nothing to rebase. Fix rounds and parallel units still leave commits worth folding, and the user asked to "club all 3 commits into one so i can see overall changes" (transcript audit, 2026-11-10). So the step matches pstack again. A pushed commit stays, because rewriting it takes a force-push.

### gitops agent

- **pstack.** No git agent. The working agent commits and runs the forge.
- **orbit.** `agents/gitops.md` runs every commit, push, rebase and forge write, with `model: sonnet` and `effort: low`. A `gitops` row in the project's Models table can change either ([Model per role](#model-per-role)). It never deletes a branch, except in shipping step 7, where it removes a landed branch's worktrees without `--force` and deletes the branch ([Shipping](#shipping)). Its tools add `ToolSearch` and two named T3 tools, `link_pull_request` and `list_thread_pull_requests`. Before linking a PR it checks for `link_pull_request` per the adapter's probe ([T3 Code host](#t3-code-host)), and that check gates only the link. When the tool is present, gitops links each PR it creates, once per PR. Asked to wait on CI, on every host, it runs orbit's `watch-pr` once with `--timeout 120` and a Bash timeout of 180000 ms, and hands a `TIMEOUT` back to the lead. It never runs `gh pr checks --watch`. It waits this way even when the lead's brief names another command or a re-check loop.
- **Why.** Orbit-only agent, so no pstack model applies. Git and `gh` work is routine, so it runs on a cheaper tier than the session by default. The cleanup exception lets gitops run the step it would otherwise stop at. T3 tools are deferred, so gitops needs `ToolSearch` to load them. In the T3 probe lane on 2026-11-16, gitops with this tool list loaded and called `list_thread_pull_requests`, and `${CLAUDE_PLUGIN_ROOT}` expanded in its body, so the watcher path resolves. Naming two PR tools keeps gitops off T3's thread, schedule and preview tools (inferred). `watch-pr --timeout 120` can exit at or after 120 s, and Bash kills a command at 120000 ms by default, so the call gets 180000 ms. gitops reports once and returns, so the lead, which stays in the thread, owns any longer wait (inferred). In one T3 lane the lead named `gh pr checks` and a periodic re-check in its brief, and gitops never probed and slept in a loop between checks (T3 lane, 2026-11-16). When the brief named no command, gitops probed and ran `watch-pr` once. The old absent branch ran `gh pr checks --watch` and ran it again when the watch timed out, which is the loop shape that lane caught. pstack has no `gh pr checks --watch`. Its babysit waits on GitHub CI with the watcher (`playbooks/babysit.md` step 6), and a code search of cursor/plugins finds the command only in `cursor-team-kit`, outside pstack (2026-11-16). So gitops waits the same way on every host, and rules.md **Host tools.** has the brief name the PR, not a command.

### Commit trailers

- **pstack.** No such hook. pstack ships no hooks (`pstack/plugin.json`).
- **orbit.** A PreToolUse hook on Bash (`hooks/no-claude-trailer.sh`) refuses a `git commit` whose command holds a `Co-Authored-By: Claude` trailer and tells the agent to commit again without it. It reads only the command, not the description.
- **Why.** Agents added the trailer despite an empty `attribution.commit` and gitops's "No trailers". Leads copied it into briefs, and later agents copied it from `git log`, so the text rule didn't hold. A hook holds it structurally (principle Encode Lessons in Structure).

### Model per role

- **pstack.** `setup-pstack` writes `~/.claude/rules/pstack-models.md` (`docs/harness/claude-code.md`). Flows name a model slot each, such as "your configured feature model" (`playbooks/feature.md`) and "your configured hillclimb model" (`playbooks/hillclimb.md`). Defaults are "`grok-4.7-xhigh-fast` for code, `claude-opus-5-5-xhigh` for prose and judgment", and the hardest changes "go to your strongest judgment model" (`poteto-mode/SKILL.md` Subagents). A grok slug maps to "Omit `model` so the agent runs on the session model". "Verification is the exception and stays on the `swarm workers` model and speed". The adapter's setup step says "Never put the role lines in `CLAUDE.md` or `AGENTS.md`."
- **orbit.** A `### Models` table in the project's Workflow block replaces most of `pstack-models.md`, with `| Task | Use for | Model | Effort |` rows (rules.md Workflow Defaults, Models). The user file `~/.claude/rules/orbit-models.md` holds rows in the same format, and `/orbit:setup` writes only its `other-family` row ([Setup](#setup)). Each cell comes from the project's table, else from the user file, else the default. The per-flow slots become per-unit work types that the project names, such as `shader-math` or `data-tuning`. The Delegate gate runs each code delegate on the work type whose Use for fits its unit, at that row's model and exact effort. A work type's cell may add `, <value> after <n> failed tries`. A failed try is a delegate whose work fails review or the check, or that crashes or returns nothing. Parallel attempts count no tries, and each part of a split unit starts at zero. A unit that fits two work types splits when each part verifies on its own, else runs as the type of its hardest part, and row order breaks a tie. A unit that turns out to fit another type is re-briefed under it, and its try count starts over. With no work types, or none that fits, a prose delegate (docs, written explanations) runs on the `judgment` role and code delegates tier by difficulty. The hardest run with `model: "opus"` (the `judgment` role). Trivial mechanical edits run on the `code` role, and so does every other delegate unless the project's `code` row is `sonnet` or `haiku`. Then the rest run on the session model. The lead's reply names each unit no work type fit. Six Task names are orbit's roles. `other-family` is a panel seat on another family under T3 Code ([Seats on another family](#seats-on-another-family)). Its empty Model takes the adapter's empty-cell default, the first roster model outside the session's family, and `inherit` keeps the session-family seat. Otherwise its Model is an ordered list of `<providerInstanceId>` or `<providerInstanceId>/<model>` entries, which tries only values from a family other than the parent's, in list order, as pstack's `arena cross-judge pool` does. A bare `<providerInstanceId>` takes that provider's first eligible model. `judgment` defaults to `opus`. It is every spawn a skill names with `model: "opus"` or as the `judgment` model, such as interrogate's first adversary, arena's first runner, autopilot owners, the `how` explainer, the `why` synthesizer and reflect's judgment reviewer, divergent reviewer and synthesizer. A skill's `model: "opus"` names that role, so it is not a step's own model. `code` defaults to `inherit`. It is interrogate's second adversary, swarm workers, `how` explorers, `why` investigators, reflect's tooling reviewer, multi-phase-plan explorers and every spawn no role or work type covers. `gitops`, `verifier` and `advisor` default to their agent's frontmatter model and effort, and rules.md Delegation hands gitops its row's model and effort when the table has a `gitops` row. `orbit:comment-sicko` takes no row and runs on its frontmatter, so a `code` row doesn't move it. Panels name their roles, so they never take a work type. The lead passes the resolved model as the `Agent` call's `model`, which overrides the agent's frontmatter, and `inherit` omits it, so the spawn gets Claude Code's default subagent model (`CLAUDE_CODE_SUBAGENT_MODEL` when set, else the session model). A step that names its own model or effort keeps it, such as `recall`'s `haiku`, the trail reviewer and multi-phase-plan's live lanes at high. rules.md's "Match the model to the job" passes an effort a step or row names as written, and otherwise picks one for the job, with no speed. The bug, feature, refactoring, perf, hillclimb and multi-phase-plan playbooks keep pstack's line minus speed, as "Pick each subagent's reasoning level for the job, per the Delegation section of rules.md." `swarm` and `arena` reword it to pick each worker's or runner's `effort` per "Match the model to the job". `interrogate` runs arena's step 3 and sets each adversary's `effort` to high ([Review](#review)). `how`, `why`, `reflect` and `show-me-your-work` drop it. The verifier takes the `verifier` row, not the `code` model, and keeps its own `effort: high` when the row names none. `agents/poteto-agent.md` carries `effort: medium` and `agents/comment-sicko.md` carries `effort: medium`, which pstack's agent files don't. The lead still picks poteto-agent's level, so its frontmatter only catches a missed pick.
- **Why.** The adapter's setup defaults map to `opus xhigh` and to `inherit-parent` for every grok role, which is orbit's `judgment` default of `opus` and `code` default of `inherit`. pstack's 17 role lines hold only those two values by default, so two roles, `judgment` and `code`, carry every default. The `how` explainer, the `why` synthesizer, reflect's judgment, divergent and synthesizer lines, and "prose and judgment" all default to `claude-opus-5-5-xhigh`, so they take `judgment`. A table in the project's AGENTS.md travels with the repo and sets the mapping where the project's cost and quality tradeoff lives. The adapter keeps one user's model picks out of the repo (inferred), and orbit's table holds the project's own work types, which belong in the repo. Which T3 providers a user has enabled is the user's, not the project's, so the `other-family` choice also lives in a user file, as pstack's model rule does, and a project row still wins. A panel seat on another provider gets a read-only `delegate_task` child when that tool is present. No other case starts a T3 thread.
- **Why.** Origin and cloud VMs are not here. pstack's template boots every lane on its own cloud VM and has no placement step. T3 test threads cluttered the sidebar and needed settling by hand (T3-native plan, rejected alternatives). A headless session with `--plugin-dir` loads the same plugin text from the head, so only behavior that calls a T3 tool needs a T3 thread (T3-native plan, Appendix C). Orbit has no `swarm workers` line, so the placeholder names the `code` role that swarm workers run on. Explorers read and report, so they take the `code` role, as `how` explorers do. Orbit's playbooks ship in the plugin, not the project's trunk. All lanes share one machine and the repo's objects. The Check line is the Workflow block's name for the repo's gates. Under Land `main` the head branch is never pushed, so the fetch would fail. A Claude Code reply is text, so it can't carry the media. Ship by default grants landing authority unless the operator opts out ([Ship by default](#ship-by-default)).

### Flow wording

- **pstack.** Bug reaches the surface "via the control skill (Non-negotiables)", refactoring "via the relevant control skill", and perf "via the matching control skill". Bug uses "Cursor's `/loop` command". Investigation re-routes "to Bug fix or Feature", says "No PR, no babysit" and "see Autonomy". Prototype says "Route to Feature".

### Waived steps

- **pstack.** No waiver rule. Prototype covers "a throwaway sketch to make a design or behavioral decision cheaply" (`poteto-mode/SKILL.md` Playbooks).

- **Why.** Orbit adds gates and ships by default, so a full flow runs where pstack's would stop at a PR. The user said "no need to put readme or commit this is just testing" and "when we are brainstorming ui dont go all the way u take forever for small changes" (transcript audit, 2026-11-10). ### Worktree cleanup

- **pstack.** The audit reads transcripts from `~/.cursor/projects/<slug>/agent-transcripts` and fetches PRs through Origin's CLI, else `gh` (`poteto-mode/scripts/worktree-audit.sh`). The pinned and active chats come "from the user or sidebar". Step 6 also clears Cursor's app state (`poteto-mode/playbooks/worktree-cleanup.md`).
- **orbit.** `/orbit:worktree-cleanup`. The audit reads `~/.claude/projects/<slug>/**/*.jsonl`. A worktree's newest session is one started in it or one of the repo's that names its path. A worktree Claude Code has locked is `hold-locked` and never removed. PRs come from `gh` only. The active sessions come from the user. The Subagents and Autonomy pointers and the Cursor app-state reclaimer are dropped.
- **Why.** Claude Code stores sessions per start path and locks a live session's worktree. Origin's CLI and the sidebar don't exist here, and Claude Code has no Cursor app state.

### Control skills

- **pstack.** Flows drive the surface with "the matching control skill", `control-ui` or `control-cli` from `cursor-team-kit`. `control-ui` creates "before/after evidence for `verify-this`".
