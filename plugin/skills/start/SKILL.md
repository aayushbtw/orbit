Goal: $ARGUMENTS

Resuming from `/orbit:session-pickup`: mark the steps the prior trail finished as done.

If Non-negotiables is not in your context, load orbit's `rules` skill first.

1. **Pick the type** from the goal: `investigate` (a question, no change), `bug` (something broken), `feature` (new behavior), `refactor` (structure only), `prototype` (a throwaway sketch to make a design or behavioral decision cheaply, or to settle an empirical fork by observing it instead of asking the human: "prototype", "mock it up", "try this layout", "sketch it to decide", brainstorming or iterating on UI the user isn't sure they'll keep), `perf` (measured slowness), `hillclimb` (sustained improvement of one metric against a target; perf is a one-off fix), `autopilot-full` (a queue of independent changes run to merged with full autonomy), `autopilot-stack` (autopilot-full without the merge, a queue of PRs built and verified with full autonomy, then handed to the operator to land), `multi-phase-plan` (a plan for work that spans phases or stacked PRs), `babysit` (an open PR driven to merge-ready: conflicts, review threads, CI). A large or cross-cutting effort (a migration across many call sites, an ambitious multi-part change), or work the user steps away from to trust later, routes to `/orbit:figure-it-out` even when a narrower flow like feature fits. Use `/orbit:figure-it-out` whenever no flow fits. A multi-phase or multi-PR plan, for work that spans phases or stacked PRs, routes to `multi-phase-plan`. Program-scale work ("run this whole project", "own this migration until it lands") routes to `/orbit:figure-it-out`, unless the goal is already a queue of PRs. A queue of independent PRs run to merged with full autonomy ("autopilot this queue", "full autopilot", one-owner-per-PR programs) routes to `autopilot-full`, not `/orbit:figure-it-out`, even when the user steps away. A queue built and verified but handed to the operator to land ("autopilot-stack", "autopilot, don't merge", "stack them, don't ship", "build the stack, I'll land it") routes to `autopilot-stack`, also not `/orbit:figure-it-out`. In a single change goal, "don't ship" or "I'll land it" keeps the flow and stops it at Opening a PR. Without them, a change ships by default, per **Ship by default** in Opening a PR. Any PR-status request ("babysit this", "get it green", "address the bugbot comments", and most often "check on PR X" or "anything outstanding on X") routes to `babysit`, and a request to land or ship a green stack runs `/orbit:ship`, each per its trigger in rules.md Non-negotiables. Ask only when the goal itself is unclear.
2. **Load the flow.** Run `/orbit:playbook <type>` with the Skill tool, or `/orbit:figure-it-out` or `/orbit:ship` when step 1 routed there. Open a todolist whose first items are the names of the matched playbook's steps and gates, copied in verbatim, before any task-specific todos. Use Claude's native task tools so the host can show progress: `TaskCreate` and `TaskUpdate` (with `TaskList` to read the existing list), or `TodoWrite` when offered. Use only tools the session offers. Without a native task tool, track the list yourself and show the user only what step 3 describes. A step you choose not to do stays in the list with a one-line `skip: <reason>`. A step the user waives ("no commit", "no subagents", "skip e2e", "just testing", "quick check") stays in the list as `skip: user waived`. "Just testing" or "quick check" waives the commit, the PR and shipping. For a change, **Opening a PR** follows the flow's steps, then, unless the user opted out, **Babysit** in `drive` mode under Land `pr` and **Shipping** last. A `prototype` is throwaway, so it ends at its **Reply:** with no Opening a PR, Babysit or Shipping. Its Principles and Stack rules hold for the whole task, and its **Reply:** names what the task reports, placed per **Final reply** in rules.md Task End.
3. **Run the list in order.** Keep the native list current: mark a step in progress when it starts and completed only when it finishes. Add task-specific items as they become known. Keep skipped steps with their `skip: <reason>` in the item text and mark them completed so they do not stay pending. On resume, update the existing list rather than creating duplicate tasks. Without a native task tool, track the step list silently and never print it. Show the user a task list only when the work is a multistep plan, meaning the goal holds two or more separate tasks the user would name, such as several fixes. Building, reviewing and landing one change is one task. Otherwise the reply states progress in a line. Each item is one of those tasks, such as `[x] Fix the login redirect` or `[ ] Add the logout button`, with a checkbox for its state. Show the task list once at the start. When a task's state changes, show only that task's line again. The final reply shows the closed task list. Each line is the task and its state, with no detail.
4. **Stay in the list.** "continue" or "do it" resumes it. "new task" starts a fresh list.
