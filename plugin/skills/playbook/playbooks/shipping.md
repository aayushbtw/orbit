### Shipping

Runs by default at task end, per **Ship by default** in `playbooks/opening-a-pr.md`, or on request.

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

The Land line in the project's Workflow block picks `pr` or `main`, and the merge method. Under Land `main` there is no PR, so a PR in the steps below is a task branch, and a stack is a chain of unpushed task branches, each child on its parent's exact tip. Step 1's verifier checks out each branch's head SHA in its own worktree, which shares the repo's objects, so an unpushed branch needs no push, and its verdict goes in the reply. In place of steps 4 and 5, fast-forward `main` through the run bottom-up, one branch at a time. gitops fetches and rebases the branch onto `origin/main`. Run the Check line, which stands in for CI, and compare the patch-id per step 3. Then gitops pushes `HEAD:main`. If `main` moved and the push is rejected, gitops fetches and rebases again, and you repeat the Check run and the comparison before it pushes. Once a branch lands, gitops rebases the next one onto the new `main` locally, moving only that branch's own commits. Nothing pushed is rewritten, so no push needs force.

1. **Verify each PR independently before it lands.** The host adapter's PR tools are the forge (rules.md Delegation, **Host tools.**). They default to the PR of this thread's branch, so every call on a PR in the run, including each gitops brief, names that PR's `number`, and `repository` when the PR is in another repo. One verifier per PR, each a fresh `orbit:verifier` with the `verifier` row's model and effort (rules.md Workflow Defaults, Models), runs the change the way a user would with the project's `verify-*` skill when it has one, else orbit's `control-ui` (UI) or `control-cli` (CLI or TUI), parent against head, and returns `PASS`, `PASS+NOTES`, or `FAIL`. It checks out SHAs, so it runs as a same-provider child per the host adapter's Where a child runs section, with role `test` and the brief the next paragraph gives the seat. Write the change's intent in one paragraph from the goal and the code. Brief the verifier with the head SHA, the parent SHA (`git merge-base <base> HEAD` in the PR's worktree, where the base is `origin/main`, or the parent's branch for a stacked PR), that paragraph, the changed paths, and the path of the project's `.claude/skills/verify-*/SKILL.md` when it has one, else the absolute path of `../control-ui/SKILL.md` or `../control-cli/SKILL.md`. gitops posts the verdict on that PR with `pull_request_respond` and no `reviewThreadId`, as one line with the verdict, its SHA, and the patch-id from `git diff <base>...HEAD | git patch-id --stable`. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.

   With a roster, when the `verifier` row's Model is `other-family` or `other-family, inherit`, each verifier is a seat on another family (`../../docs/harness/t3-seats.md`), picked as the `other-family` row picks its seat. A `verifier` Model that is a target on another provider makes each verifier that seat too, with the target as its one entry and no family check. When it is unavailable, the verifier asks or holds as below (`../../docs/harness/t3-seats.md`). Only the agent whose turn end returns to the user fills it. Autopilot owners and swarm lanes take the T3 otherwise column of Where a child runs and stay on the lead's provider. Spawn one `delegate_task` child per PR with `isolation: "worktree"`. Its brief names the absolute path of `../../agents/verifier.md` as the instructions to read first and states its `tools` limit: it runs commands and writes scratch scripts in its own worktree, and edits, commits and pushes nothing in the repo. It carries the head SHA, parent SHA, intent paragraph, changed paths and skill path above. It asks the child to report its worktree's absolute path (`pwd`) and starting branch (`git branch --show-current`, before any checkout), so you can remove it once you settle the child. It says "If you cannot run the change in this environment, reply with the first line `BLOCKED: <reason>`, not FAIL." On `BLOCKED` or a failed child, put `<entry> unavailable: <reason>` in the reply and try the next candidate. When none is left, run a native `orbit:verifier` as above only when the `verifier` row's Model is `other-family, inherit`, the user's yes to a native verifier. Otherwise write one `<entry> unavailable: <reason>` line per entry in the reply, each on its own line, with `send_to_user`, before any question or hold. Then ask the user before a native verifier runs, offering it without marking it recommended, or hold the PR and say so when no user can answer. A `FAIL` stands. Settle each child thread once you have read its verdict. A stack of N PRs opens N child threads, and they count toward the Parallel cap (rules.md Workflow Defaults).

   Before any verifier spawns, brief `orbit:advisor` for a diff review of each PR, on the `judgment` model (rules.md Workflow Defaults, Models). When the `judgment` cell holds a target, the review runs as the host adapter's A cell that names a provider says. The brief holds `git diff <parent>..<head>`, the intent paragraph, and the project sources for the changed paths, gathered as the Plan gate in `SKILL.md` gathers them. It asks for blocking findings, meaning bugs, broken project rules and missed cases. Check each blocking finding against the code, and dismiss one that doesn't hold, with its reason in the reply. Each one that holds gets a fix round through the Delegate gate. Under Land `pr`, gitops pushes the fix, and Babysit (`playbooks/babysit.md`) brings the PR and every PR stacked above it back to merge-ready before any verifier spawns. Non-blocking findings left unfixed go in the reply. The review covers the patch it read. It runs again, on `git diff <reviewed-sha>..<head>`, only when step 3 finds that patch changed, or after a fix for a `FAIL` and before the next verifier. The review is not a verdict, because only the verifier runs the change, and it never replaces the verifier. The advisor is a foreground `Agent`, as the host adapter's Where a child runs section says for a read-only child, unless the `judgment` cell holds a target, as above. Only the agent whose turn end returns to the user runs the review, so an autopilot owner or swarm lane never does.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a verifier run stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and step 1's diff review, because the old verdict never saw it. A run with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted. For each PR whose verdict stands, record its accepted merge target `(PR, base, head)`, meaning its `number`, its `baseBranch` and the `headSha` the verdict covers.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR. The gitops brief carries that PR's accepted `(PR, base, head)` from step 3 verbatim. gitops reads the PR with `pull_request_read` and confirms that `headSha` equals the accepted head and `baseBranch` equals the accepted base. If either moved, gitops stops without merging and reports the drift. You then repeat step 3's patch-id and evidence checks, and step 1 when the patch drifted, before you retry. gitops merges with `pull_request_merge`, `expectedHeadSha` set to the accepted head, never a SHA no verdict covers, and `method` from the Land line, `squash` by default. It never passes `auto: true` or `stack: true`, because T3's auto-merge also merges later pushes that no verdict covers, and a stack merge lands the layers below without pinning each layer's accepted head. When checks are still pending, gitops returns without merging. You wait per **Host watcher** in `playbooks/babysit.md`, and on the wake the next gitops brief confirms `(base, head)` again and merges once checks pass. A PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back with `pull_request_read` for the result, because a merge call can report success when a merge queue only queued the PR. A PR has landed only when `state` reads `merged` and `baseBranch` reads the intended trunk. A PR that reads `closed` without merging is a terminal block. Stop at that layer and every layer above it, and never retarget, rebase or merge a layer above it. After a merge lands, read the PR whose base was the merged branch. GitHub moves that base to trunk once the merged branch is deleted. Use T3's base retarget instead if `pull_request_update` gains a `base` field. Until then, when the base still names the merged branch, gitops deletes that branch only while it still points at `<tip>`, the merged PR's last `headSha`. gitops first checks the remote ref with `git ls-remote origin refs/heads/<merged branch>`. If it prints nothing, the branch is already gone, so gitops skips the delete and goes straight to reading back the child PR's `baseBranch`. Otherwise, in a separate call, it deletes with `git push --force-with-lease=refs/heads/<merged branch>:<tip> origin :refs/heads/<merged branch>`, never an unguarded `git push origin --delete`. If `ls-remote` shows another SHA or the push is rejected, gitops keeps the branch and stops, and you report that the merged parent branch moved. After the delete, gitops reads the child PR with `pull_request_read`. Its `baseBranch` must equal the intended trunk before any rebase or merge. If the forge does not confirm the new base, stop and report. Then gitops moves its patch onto the merge result. After a fetch, it runs `git rebase --onto origin/<trunk> <tip>`, where `<tip>` is the merged PR's last `headSha`, so commits a squash merge replaced don't replay. Then it pushes with `--force-with-lease` pinned to the SHA you last pushed or took over. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives, against the new accepted `(PR, base, head)` that step 3 records.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Read the run bottom-up per **Host watcher** in `playbooks/babysit.md`, until the ceiling reads `COMPLETE` with `baseBranch` equal to the intended trunk. A PR that reads `CLOSED` is a terminal block. The run stops at that layer, and every layer above it stays as it is. A PR that reads `merged` on a non-trunk base is a terminal block and stops the run the same way `CLOSED` does. `CLOSED` never counts as `COMPLETE` at the ceiling. A frontier that waits on your own next step-4 merge is not a handback. Run that merge and read again. When a merge queue, auto-merge or a person holds the merge, watch per **Host watcher** and end the turn, because the merge wakes you. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1. Before you hand back, unwatch each PR you watch, per **Host watcher** in `playbooks/babysit.md`.
7. **Clean up each branch that landed.** A branch has landed once its `HEAD:main` push succeeds under Land `main`, or once `pull_request_read` reads `state` as `merged` and `baseBranch` as the intended trunk under Land `pr`. A PR that reads `closed` without merging never landed, so its branch and worktrees stay. The thread keeps the task worktree it is bound to and that branch, because removing a thread's working directory breaks its later shell calls, and the reply names them. gitops, from the thread's directory, removes every verifier and owner worktree still left for the task with `git worktree remove <absolute path>`, never `--force`. The lead already removed each settled child's worktree. A worktree with uncommitted changes stays. Then gitops deletes each other local branch of the task with `git branch -D <branch>` only when it holds nothing unlanded. Under Land `main`, gitops fetches, and the test is `git merge-base --is-ancestor <branch> origin/main`, because the push leaves the project root's `main` behind, so `-d` refuses. gitops never switches, merges or fast-forwards the project root's checkout, because it is the user's. Under Land `pr`, the test is a local tip equal to the PR's last `headSha`, because a squash merge leaves its commits off trunk. A branch that fails its test stays. The reply names each worktree and branch that stays.

**Reply:** what landed and how you confirmed it, in the outcome. As Heads-up items: the ceiling when the run stopped short, each PR whose verdict is not a plain `PASS`, with its verdict line and notes, a verifier or reviewer that ran on a fallback, each non-blocking finding left unfixed, each worktree or branch kept with its reason, and what the next gap needs.
