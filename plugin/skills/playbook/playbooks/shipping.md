### Shipping

Runs by default at task end, per **Ship by default** in `playbooks/opening-a-pr.md`, or on request.

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

The Land line in the project's Workflow block picks `pr` or `main`, and the merge method. Under Land `main` there is no PR, so a PR in the steps below is a task branch, and a stack is a chain of unpushed task branches, each child on its parent's exact tip. Step 1's verifier checks out each branch's head SHA in its own worktree, which shares the repo's objects, so an unpushed branch needs no push, and its verdict goes in the reply. In place of steps 4 and 5, fast-forward `main` through the run bottom-up, one branch at a time. gitops fetches and rebases the branch onto `origin/main`. Run the Check line, which stands in for CI, and compare the patch-id per step 3. Then gitops pushes `HEAD:main`. If `main` moved and the push is rejected, gitops fetches and rebases again, and you repeat the Check run and the comparison before it pushes. Once a branch lands, gitops rebases the next one onto the new `main` locally, moving only that branch's own commits. Nothing pushed is rewritten, so no push needs force.

1. **Verify each PR independently before it lands.** GitHub CLI (`gh`) is the forge. One verifier per PR, each a fresh `orbit:verifier` spawned with the `verifier` row's model and effort (rules.md Workflow Defaults, Models) and `isolation: "worktree"`, runs the change the way a user would with the project's `verify-*` skill when it has one, else orbit's `control-ui` (UI) or `control-cli` (CLI or TUI), parent against head, and returns `PASS`, `PASS+NOTES`, or `FAIL`. In T3 Code with `delegate_task`, that verifier checks out SHAs, so it runs as a same-provider child per the host adapter's Where a child runs section (rules.md Delegation, **Host tools.**), with role `test` and the brief the next paragraph gives the seat. Write the change's intent in one paragraph from the goal and the code. Brief the verifier with the head SHA, the parent SHA (`git merge-base <base> HEAD` in the PR's worktree, where the base is `origin/main`, or the parent's branch for a stacked PR), that paragraph, the changed paths, and the path of the project's `.claude/skills/verify-*/SKILL.md` when it has one, else the absolute path of `../control-ui/SKILL.md` or `../control-cli/SKILL.md`. gitops posts the verdict on that PR with `gh pr comment`, as one line with the verdict, its SHA, and the patch-id from `git diff <base>...HEAD | git patch-id --stable`. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.

   Under T3 Code with a roster, when the `verifier` row's Model is `other-family` or `other-family, inherit`, each verifier is a seat on another family (`../../docs/harness/t3-seats.md`), picked as the `other-family` row picks its seat. Only the agent whose turn end returns to the user fills it. Autopilot owners and swarm lanes take the adapter's absent column and stay on the lead's provider. Spawn one `delegate_task` child per PR with `isolation: "worktree"`. Its brief names the absolute path of `../../agents/verifier.md` as the instructions to read first and states its `tools` limit: it runs commands and writes scratch scripts in its own worktree, and edits, commits and pushes nothing in the repo. It carries the head SHA, parent SHA, intent paragraph, changed paths and skill path above. It asks the child to report its worktree's absolute path (`pwd`) and starting branch (`git branch --show-current`, before any checkout), so you can remove it once you settle the child. It says "If you cannot run the change in this environment, reply with the first line `BLOCKED: <reason>`, not FAIL." On `BLOCKED` or a failed child, put `<entry> unavailable: <reason>` in the reply and try the next candidate. When none is left, run a native `orbit:verifier` as above only when the `verifier` row's Model is `other-family, inherit`, the user's yes to a native verifier. Otherwise write one `<entry> unavailable: <reason>` line per entry in the reply, each on its own line, with `send_to_user` when it is present, before any question or hold. Then ask the user before a native verifier runs, offering it without marking it recommended, or hold the PR and say so when no user can answer. A `FAIL` stands. Settle each child thread once you have read its verdict. A stack of N PRs opens N child threads, and they count toward the Parallel cap (rules.md Workflow Defaults).

   Before any verifier spawns, brief `orbit:advisor` for a diff review of each PR, with the `judgment` model (rules.md Workflow Defaults, Models) as the `Agent` call's `model`, not the advisor's Fable, because a review per PR spends too much of Fable's usage limit. The brief holds `git diff <parent>..<head>`, the intent paragraph, and the project sources for the changed paths, gathered as the Plan gate in `SKILL.md` gathers them. It asks for blocking findings, meaning bugs, broken project rules and missed cases. Check each blocking finding against the code, and dismiss one that doesn't hold, with its reason in the reply. Each one that holds gets a fix round through the Delegate gate. Under Land `pr`, gitops pushes the fix, and Babysit (`playbooks/babysit.md`) brings the PR and every PR stacked above it back to merge-ready before any verifier spawns. Non-blocking findings left unfixed go in the reply. The review covers the patch it read. It runs again, on `git diff <reviewed-sha>..<head>`, only when step 3 finds that patch changed, or after a fix for a `FAIL` and before the next verifier. The review is not a verdict, because only the verifier runs the change, and it never replaces the verifier. Under T3 Code the advisor is a foreground `Agent`, as the host adapter's Where a child runs section says for a read-only child. Only the agent whose turn end returns to the user runs the review, so an autopilot owner or swarm lane never does.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a verifier run stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and step 1's diff review, because the old verdict never saw it. A run with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR. gitops merges it with `gh pr merge <pr> --delete-branch` and the Land line's merge method, `--squash` by default. A PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm `--auto` (GitHub auto-merge) only on a PR whose verdict covers its current head, because it lands whatever head is ready. After a merge lands, have gitops retarget the PR whose base was the merged branch to trunk (`gh pr edit <pr> --base <trunk>`) and move its patch onto the merge result. After a fetch, gitops runs `git rebase --onto origin/<trunk> <tip>`, where `<tip>` is the merged PR's `headRefOid`, so commits a squash merge replaced don't replay. Then it pushes with `--force-with-lease` pinned to the SHA you last pushed or took over. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Watch the run with `scripts/watch-pr/watch-pr --queued-stack` per **Host watcher** in `playbooks/babysit.md`, until it reports `COMPLETE` at the ceiling. Pass the run's PR numbers, bottom-to-top, in `--stack-prs`, and pass the same list each time you restart the watcher. In T3, a `queued-stack` timeout whose `waitingOn` is `merge` is not a handback when that merge is your own next step-4 merge. Run it and read again. In T3 with `watch_pull_request` present, when a merge queue, auto-merge or a person holds the merge, watch per **Host watcher** and end the turn, because the merge wakes you. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1. Before you hand back, unwatch each PR you watch, per **Host watcher** in `playbooks/babysit.md`.
7. **Clean up each branch that landed.** A branch has landed once its `HEAD:main` push succeeds under Land `main`, or once `gh pr view <pr> --json state` reads `MERGED` under Land `pr`. First leave the session's own worktree with `ExitWorktree` and `keep`, which ends its isolation (rules-shared.md Bash). Never pass `remove`, which refuses a landed branch, or `discard_changes`, which is the user's call. A session that never called `EnterWorktree` skips the exit. If its working directory is the task worktree, as in a T3-bound thread, it keeps that worktree and its branch, because removing a thread's working directory breaks its later shell calls. Then gitops, from the session's directory, removes the task's worktree and every verifier and owner worktree still left for it with `git worktree remove <absolute path>`, never `--force`. In T3 Code the lead already removed each settled child's worktree. A worktree with uncommitted changes stays. Then gitops deletes the local branch with `git branch -D <branch>` only when it holds nothing unlanded. Under Land `main`, gitops fetches, and the test is `git merge-base --is-ancestor <branch> origin/main`, because the push leaves the restored checkout's `main` behind, so `-d` refuses. gitops never switches, merges or fast-forwards that checkout, because it is the user's. Under Land `pr`, the test is a local tip equal to the PR's `headRefOid`, because a squash merge leaves its commits off trunk. A branch that fails its test stays. The reply names each worktree and branch that stays.

**Reply:** what landed and how you confirmed it, in the outcome. As Heads-up items: the ceiling when the run stopped short, each PR whose verdict is not a plain `PASS`, with its verdict line and notes, a verifier or reviewer that ran on a fallback, each non-blocking finding left unfixed, each worktree or branch kept with its reason, and what the next gap needs.
