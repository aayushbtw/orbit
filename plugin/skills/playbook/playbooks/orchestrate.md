### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is a normal flow under a session override ("run until done"). One ambitious run that needs a bespoke workflow is `/orbit:figure-it-out`. Work that one agent could finish inside the session's budget is not a program.

Under Land `main`, a PR here means a task branch, its merge is gitops pushing `HEAD:main` per the Land `main` paragraph of `playbooks/shipping.md`, and the Check run there stands in for green CI.

Run it with your own tools. Spawn workers with the `Agent` tool. Keep the program's state in `notes.md` in the program's store, `<git common dir>/orbit-orchestrate/<slug>/`, with the git common dir from `git rev-parse --path-format=absolute --git-common-dir`, so every worktree reaches it and the OS never clears it. Watch each PR with PR and CI event subscriptions when your harness has them. You call no scripts, run no polling loops, and never relay messages or status between agents. Owners still run their babysit watcher per `playbooks/babysit.md`.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Its `Agent` settings, brief, trail, `agents.tsv` row and fresh agent for each later round follow step 2 of `playbooks/autopilot-full.md`, as does "Never message an owner that returned". Its trail and `agents.tsv` go in this program's store. A stacked owner's base is its parent's branch and exact tip SHA, per step 2 of `playbooks/autopilot-stack.md`. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers can't see their siblings. Each worker is an `Agent` call with `isolation: "worktree"`, omitted only when the work needs something a fresh worktree lacks, such as uncommitted files in another checkout. A runtime check uses the project's `verify-*` skill, else `/orbit:control-ui` or `/orbit:control-cli`. Each kickoff carries this line verbatim, "You run on the user's machine, not a VM. Run the app headless or windowless when the project allows it, and never open a window that takes focus or plays sound unless the user agreed." Pick each subagent's reasoning level for the job, per the Delegation section of rules.md.
- **Keep up to the Parallel cap (rules.md Workflow Defaults) in flight,** and start the next one as each finishes instead of waiting on a whole batch.
- **New work that needs a worker's built state,** such as its checkout or uncommitted changes, goes to a fresh agent briefed with that worker's report. Its brief says to call `EnterWorktree` with `path` set to that worker's worktree before any other work, as step 2 of `playbooks/autopilot-full.md` does. Never message an agent to check on it, because a message restarts an idle agent.
- **Each PR gets a verifier that isn't its author,** a fresh `orbit:verifier` spawned per step 1 of `playbooks/shipping.md`. The owner merges only on that verifier's pass at the current head.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a control-skill check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks`, not the worker's last report. Under Land `main`, the live state is the branch tip against `origin/main` and the Check run. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, or under Land `main` its commits and trail rows, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
