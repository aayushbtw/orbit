# Seats on another family

Read this file after `t3-code.md` when the `other-family` Models row lists providers, or the `verifier` row's Model is `other-family` or `other-family, inherit`. Probe and Where a child runs are sections of `t3-code.md`, in this folder, and paths here are relative to orbit's plugin folder, two levels above this file's folder.

A skill may name a seat on another family, such as arena's cross-judge, interrogate's second adversary, the show-me-your-work trail reviewer or autopilot-full's audit seat. The session-family seat is the seat the skill names, run on the session's own family as an `Agent` spawn. Fill one such seat per panel. Only the agent whose turn end returns to the user fills a roster seat. A subagent takes the absent column, because its turn end returns to its parent and the child's wake lands on the lead's thread. Seats that write the change's code, such as arena runners, delegates, swarm workers and live lanes, never take a roster seat. They run on the lead's provider, as Where a child runs says.
When the `verifier` row's Model is `other-family` or `other-family, inherit`, each verifier that shipping step 1 spawns is such a seat too (`skills/playbook/playbooks/shipping.md`). It fills one seat per PR, not one per panel.

Probe `orchestrator_capabilities`, `delegate_task`, `task_status`, `task_cancel` and `t3_thread_organize` as Probe says. If any is absent, the absent column applies.

The Seats on another family section of `t3-code.md` says when to call `orchestrator_capabilities`, what its result holds, and how a row's Effort becomes `target.options`.

The session's family is the `driverKind` of the provider whose `providerInstanceId` equals `inheritedProviderInstanceId`. The `other-family` row of the Models table picks the seat, with each cell resolved as rules.md Workflow Defaults, Models says. The roster is the ordered list of entries in that row's Model cell. An entry is a bare `<providerInstanceId>` or `<providerInstanceId>/<model>`, split at the first `/` because a model id can hold one. `inherit` is valid only as the last entry. An empty cell, no row and `inherit` give no roster, so the skill's own branch for a host with no roster runs. The cell resolves to one of four outcomes.

| Model cell | What runs | Reply line |
| --- | --- | --- |
| Empty, or no row | The skill's session-family seat, as outside T3. | `No seat on another family is configured. /orbit:setup lists providers.` |
| `inherit` | The skill's session-family seat. | None. |
| A list | The first candidate that returns a result. Candidates are tried in list order, at most three. | `<entry> unavailable: <reason>` for each entry that fails a check or whose child fails. |
| A list whose every candidate fails | No seat. A list that ends with `inherit` runs the session-family seat instead. | `Skipped <skill>'s seat on another family: every listed entry failed.` |

**A list.** Build the candidates once, before the first spawn. Walk the entries in list order, and stop at the third candidate.

1. Skip an entry whose provider's `driverKind` is the session's family, with no line.
2. An entry whose provider already gave a candidate is `<entry> unavailable: provider already a candidate`. Each candidate has its own `providerInstanceId`.
3. The provider must hold. It is in `providers`, is enabled, has `canRunCrossProviderChildTask` true and has a non-empty `models` list. A seat that runs commands, such as interrogate's roster adversary or the verifier seat, also needs the parent's runtime mode in the provider's `runtimeModes` when the provider lists them. A provider without that mode steps the child down to a narrower mode, which can ask for approval on commands and stall on the user, so the entry is `<entry> unavailable: runtime mode <mode> not offered`.
4. The entry's model must pass the family check. A bare entry picks its model first.
5. A `<providerInstanceId>/<model>` entry holds when that provider lists the model. The first result is a short list, so before you call the model not listed, call `orchestrator_capabilities` with `search` set to the model id.

An entry that fails a check puts `<entry> unavailable: <reason>` in the reply. So does a candidate whose child errors, hits a limit, returns nothing or replies `BLOCKED`, before you try the next candidate. The reason quotes the child's error or its `BLOCKED` line, or names the limit or the empty result. For a failed check, the reason quotes the provider's `constraints` verbatim or names the check that failed. Never fill the seat from a provider the list does not name, and never replace an entry without saying so.

**Family check.** A model's family word is the text before the first `-` in the last `/` segment of its `id`. `claude-opus-5-5` and `anthropic/claude-x` give `claude`, and `gpt-6.1-sol` gives `gpt`. An `id` with no `-`, such as the alias `opus`, has no family word. A model whose `id` is `auto` or `default` is opaque, and has no family word either. The capabilities result has no field that says what such a model runs.
The session's family word is that of `inheritedModel`. When `inheritedModel` has none, take the family word of the first model that the session's own provider lists whose `id` has a family word and holds `inheritedModel` as a token. When that finds none, the session's family is unknown. Then no entry fails the family check on that ground, and every seat's reply says `family unverified`. Only `inheritedModel` sets the family word, because an aggregator lead lists models of several families.
A model is of the session's family when any token of its `id`, split at `-`, `/`, `.` and `:`, equals the session's family word or names that family's vendor. The vendors are `anthropic` for `claude`, `openai` for `gpt` and `xai` for `grok`. So `anthropic/x` is of a Claude session's family, although `x` has no family word. Such an entry is `<entry> unavailable: <model> is the session's family`. The family check runs before the listing check, so under a Claude lead `codex/claude-opus-5-5` fails with no `search` call. An opaque model fails no family check.

**Model for a bare entry.** A bare `<providerInstanceId>` takes the provider's first listed model that is neither opaque nor of the session's family. It takes an opaque model only when every model the provider lists is opaque. An explicit `<providerInstanceId>/default` takes `default` as named. When the provider has no model to take, the entry is `<entry> unavailable: no model outside the session's family`. The reply says `family unverified` beside the provider and model of a seat on an opaque model, and never says that its panel has a second family.

**Every candidate fails.** The list fails when no entry passes the checks, or when each candidate's child errors, hits a limit, returns nothing or replies `BLOCKED`. Before you try the next candidate, `task_cancel` a child that still runs. Never try a fourth candidate. When no candidate is left, skip the seat, so neither a roster seat nor the session-family seat runs. The skill reports the skip line where the seat's result would go and takes no other branch for that seat. Arena picks its base without a judge, interrogate runs its first adversary alone, and autopilot-full's verdict goes on without its audit seat. A skipped trail reviewer makes the show-me-your-work Attention section open with `not reviewed: seat on another family skipped`, and the lead never reviews its own trail in the reviewer's place. A list that ends with `inherit` runs the session-family seat instead, because the user wrote that fallback, and the reply says which seat ran. The verifier seat never skips, as below.

When no provider's `providerInstanceId` equals `inheritedProviderInstanceId`, the session's provider is unknown, so say so in the reply. With a list, try no entry and skip the seat. A list that ends with `inherit` still runs the session-family seat, and the verifier seat still never skips, as **Every candidate fails** says. With no list, use the session-family seat.

Spawn the seat with `delegate_task`, `target: {providerInstanceId, model, options}`, `role: "review"`, `mode: "async"`, a `title` naming the skill and the seat, a `clientRequestId` naming the skill, the seat and the round, and no `runtimeMode`. A retry of the same call after a tool error or a lost response reuses that `clientRequestId`, so T3 returns the same child and starts no second one. A new round and a fallback to the next candidate each take a new one. A new round's brief carries the original brief, the prior round's findings, the responses to them and the objections still open. A seat that only reads keeps the default `isolation`. Interrogate's adversary runs repros, so its skill gives it a worktree and its own brief line. A child on another provider gets none of this thread's context, so the brief stands alone. It holds the user's goal in one line, the absolute path of each file to read, the seat's prompt, and "You are a subagent of this thread. Do not edit any file. Return your findings as text." That first sentence keeps a child that loads orbit's rules from acting as a lead. It never holds a secret.
The verifier seat is the second seat that runs code, so like interrogate's adversary it gets `isolation: "worktree"` and its own brief line. In place of the no-edit line, its brief states the verifier's `tools` limit and asks for the first line `BLOCKED: <reason>`, not FAIL, when the change cannot run in that environment. On `BLOCKED` or a failure, put `<entry> unavailable: <reason>` in the reply and try the next candidate. When none is left, run the native verifier only when the `verifier` row's Model is `other-family, inherit`, and say so. Setup writes that `inherit` only after the user's yes to a native verifier. A trailing `inherit` on the `other-family` row covers panel seats, not the verifier. Otherwise write one `<entry> unavailable: <reason>` line per entry in the reply, each on its own line, before any question or hold. Never merge the reasons into the question. Send those lines with `send_to_user` when it is present, before the question, because T3 may show text written before a tool call only as a one-line summary. Then ask the user before a native verifier runs, because nothing lands without a verifier. The question offers the native verifier without marking it recommended, because the `verifier` row withholds the yes that a trailing `inherit` gives. With no user to ask, as in an unattended autopilot run, hold the PR and say so. With no roster, the native verifier runs, as the table's first two rows say.
`t3_thread_send` only answers or steers a running child. Every re-check or new review round is a new `delegate_task` with a new `clientRequestId`, because T3's thread rules say "Every new delegate review or re-check is a new `delegate_task` (brief, findings, objections), never a `t3_thread_send`."

Start the panel's other seats too, then keep working or end the turn, as Where a child runs step 6 in `t3-code.md` says. The child's completion brings the wake that step defines. When a `delegate_task` result carries `next`, follow it and do not poll. Read the result with `task_status`. Then check `git status --short` for edits, and settle the child thread with `t3_thread_organize` action `settle`, with `threadId` set to the `childThreadId` that `delegate_task` returned.

When a child fails, try the next candidate as **Every candidate fails** says. The reply names each seat's provider and model.
The end of Where a child runs says when to read and settle the child, how to stop or archive it, how to answer its question and how the reply names it.
