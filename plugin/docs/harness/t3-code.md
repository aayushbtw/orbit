# Orbit in T3 Code

Orbit runs in T3 Code only. This is its host adapter, at the path pstack uses for one. Orbit's skills come from pstack, which uses Cursor names, and orbit's text names Claude Code's tools, as pstack's Claude Code adapter maps them. This file maps both onto T3 Code's tools. Read it once per session, before the first step that opens, reads, pushes to or waits on a PR, files an issue, needs a worktree, schedules a wake or routine, asks for a secret, renders a verdict's proof table, fills a panel seat on another family, runs a spawn whose Models cell names a provider, would start a child thread, runs a browser or device step the user asked for, or spawns a child in plan mode. Never pass a field or value the tool schema rejects.

## Probe

T3 Code serves its tools as MCP tools named `mcp__t3-code__<name>`, and most of them are deferred. Before calling a T3 tool, check that tool itself. It is present when it is already in your tool list, or when your tool search (`ToolSearch` with `select:mcp__t3-code__<name>`) loads it. T3 tools may load late. Try a missing tool's name once, by tool search or else by its first real call, before you call it absent. Never key on an environment variable, a path, or another tool of the same family, because T3 can turn one tool off and leave the rest. Each subagent checks for itself, and T3 hides some tools, such as the PR watch tools, from subagents.
When a call returns an error that the tool needs an agent running inside T3 Code, treat that tool as absent, and with it the tools that act as the calling thread, which cover subagents, secret requests, rendered HTML, the browser preview, devices and worktree handoff. Never call `t3_thread_launch` in their place unless the user asked for a new thread.

A step whose tool is absent does what **When a tool is absent** below says. Never replace a T3 tool with a shell CLI for the same forge, a sleep or poll loop, or another host's tool.

## Any lead

In T3 Default mode you are already executing. A playbook's Plan gate is a review step within the current mode. Your tool list may hold a plan-mode exit tool, such as `ExitPlanMode` or `exit_plan_mode`. Call it only when the operator put the thread in plan mode and gave the plan a go. Never call it on a wake-up, before a tool call or to restate a plan. A step you can take now gets no written plan.

Orbit's text names Claude Code's tools and skill syntax. A tool that your tool search can load counts as in your tool list. When your tool list lacks one, or your host leaves the syntax in place, use your own equivalent, as the table below says. Every row keys on what you have, never on which provider runs you.

### When a tool is absent

Put one line in the reply, `<tool> unavailable: <reason>`, and go on to the next step. Do not stop, ask or retry. When a later step needs what the skipped step made, such as a URL or a key, leave a placeholder and name it in the line.

- `pull_request_create`: gitops pushes the branch with `git push -u origin <branch>`, and the line names the branch, so the user opens the PR.
- `pull_request_read`, `ci_logs` or `pull_request_respond`: Babysit reports what it could not read or answer and hands back.
- `pull_request_merge`: Shipping verifies as usual and stops before step 4, and the reply names the verified run for the user to merge.
- `watch_pull_request`: the lead runs one `pull_request_read` per turn, reports it and hands back. An unattended hillclimb's merge wait takes its `schedule_task` heartbeat instead.
- `create_issue`: the line carries the issue's title and evidence for the user to file.
- `t3_worktree_handoff`: run `git worktree add <path> -b <type>/<slug> origin/<trunk>` and work there by absolute path.
- `schedule_task`, `request_secret`: skip the step.
- `html_preview` or `html_render`: an in-chat table, as swarm Phase D's result table (`skills/swarm/SKILL.md`). A chart is a Mermaid chart (`xychart-beta` or `pie`).
- `preview_*`: the control-ui harness (`skills/control-ui/SKILL.md`).
- `t3_background_wait`: the notification a background task sends when it finishes.
- `delegate_task` or its companions in Where a child runs step 1: that section's T3 otherwise column.

## Where a child runs

Find the row for what the child needs and the column for where you run. The lead is the agent whose turn end returns to the user. T3 otherwise means you are a child or a subagent, or `delegate_task` is absent. No `Agent` call passes `isolation: "worktree"`. A child whose Models cell holds a target on another provider runs as A cell that names a provider says, whatever its row here. A target on your provider keeps its row.

| Child | Lead with `delegate_task` | T3 otherwise |
| --- | --- | --- |
| Shares your checkout or works in one that exists, such as a read-only child (the `how` explainer, the advisor, a judge on the session's family, a verify lane that reads a SHA from an export, a swarm worker that only reads), gitops, a serial delegate, a fix round, comment-sicko, or an owner's fix or rebase round in the owner's worktree | `Agent` with `run_in_background: false` and no `isolation`. | Same as the lead. |
| Needs its own checkout, such as a parallel delegate, an arena runner, an interrogate adversary, a swarm worker that writes, or the native verifier | Same-provider `delegate_task`, as the list below says. | One unit at a time in your own checkout. Never make a checkout in the shell. The verifier never detaches or moves a ref in your checkout or a dirty task worktree. It verifies from read-only exports in export mode, or replies `BLOCKED`, as `agents/verifier.md` says. |
| Runs while you keep working, such as an autopilot owner's build round | Same-provider `delegate_task`, as the list below says. | One at a time, as a foreground `Agent` with no `isolation`. The reply says the tick cannot fire while it runs. |
| A panel seat on another family, such as arena's roster judge, or the verifier seat on another family | A roster seat, as `t3-seats.md` says. | The session-family seat, as Seats on another family says. |

A same-provider child runs this way.

1. Probe `orchestrator_capabilities`, `delegate_task`, `task_status`, `task_cancel` and `t3_thread_organize` as Probe says. Call `orchestrator_capabilities` once per thread, as Seats on another family says.
2. Commit what the child needs on the task branch first, because T3 does not copy uncommitted edits. T3 starts the child's checkout at HEAD of this thread's bound checkout, else of the project root. So the brief names the start SHA, your checkout and the project root, both paths as `git rev-parse --show-toplevel` prints them. The child's first command is `git rev-parse --show-toplevel`, and when it prints either path the child stops and reports without moving HEAD, because a child that got no worktree runs in this thread's bound checkout. A verifier is the exception, because it checks three paths and switches to export mode in place when its guard trips, as `agents/verifier.md` says, so it never stops there. Next it runs `git reset --hard <start sha>`, which moves its own fresh branch there. For a unit that builds on the task branch, the start SHA is the task head after this commit. For an owner or other work off trunk, it is the SHA of `origin/<trunk>` after a fetch, and for an owner whose PR stacks on another PR, that PR's tip (`skills/playbook/playbooks/autopilot-stack.md` step 2). Step 10's fresh round runs its own `git switch -C <branch> <head sha>` in place of the reset. A verifier or adversary checks out the SHAs its brief names in place of the reset, which pins it the same way.
3. Call `delegate_task` with `isolation: "worktree"`, `mode: "async"`, a `clientRequestId` as step 4 says and no `runtimeMode`. Set `target.providerInstanceId` to `inheritedProviderInstanceId`, or to the target's provider when the spawn's Models cell names one (A cell that names a provider). Set `target.model` to that provider's id for the model the spawn's Models role resolves, which for a target is its model part, and omit it for `inherit`. Pass the role's effort in `target.options` as Seats on another family does, else `options: []`. `role` is `implementation` for a writer or an owner, `review` for an adversary and `test` for the verifier. `title` names the skill and the unit.
4. `clientRequestId` is `<skill>-<unit>-<short base sha>-try<n>`. A retry of the same call after a tool error or a lost response reuses it. A new try or round takes a new one.
5. When the spawn names an `orbit:` agent, the brief names the plugin folder as an absolute path and the agent file to follow, `agents/<name>.md` in that folder, because a child thread loads no agent, and states the agent's `tools` limit. A `general-purpose` child, such as an owner, a swarm worker or an adversary, gets the plugin folder and the playbook `SKILL.md` path instead. Every brief says "You are a subagent of this thread. Start no child thread." It tells the child to commit its unit by path itself and to report its worktree path from `pwd`, its branch and the commit SHA. An owner's brief also allows native subagents in the foreground and ends the build round with one `pull_request_read` and its PR line, as `skills/playbook/playbooks/autopilot-full.md` step 2 says. It carries that step's build contract verbatim, which runs `/orbit:start <item>, don't ship`, names the one branch the owner may write, and says "Never merge a PR, never push `<trunk>`.", because only the lead lands. Under Land `main`, the owner stops at the committed local branch and pushes nothing. A verifier's brief also names your checkout, the task worktree path and the project root path, each as `git rev-parse --show-toplevel` prints it, and the verifier proves a separate checkout against all three before it moves HEAD.
6. The result carries `next`. Follow it and never poll. T3 tells you when the child finishes, and that notice is the wake. Keep working while other work is left, and end the turn only when none is left. With a turn running, the wake arrives inside that turn, beside the next tool result, and names the task, the child thread, its status and the child's result text. With no turn running, the wake is a new run after the turn ends. So ending the turn never loses a wake. A wake that arrives in the middle of a step, such as a review or another child's cherry-pick, waits until that step is done. Handle each wake once, so a wake you already handled needs no second `task_status` after a later turn ends.
7. On the wake, use the completed result already in the thread. If the wake supplies no result, read the child result once. Check `git merge-base --is-ancestor <start sha> <sha>`. A commit that does not descend from the start SHA is a failed try, never cherry-picked. A child that stopped at step 2's guard is a failed try too, and its unit reruns serially in the task worktree, not as a new delegate. A verifier is the exception. It never reruns in the task worktree, and never detaches or moves a ref in your checkout or a dirty task worktree. On step 2's guard it already switched to export mode in place, as `agents/verifier.md` says, so its verdict stands and nothing reruns. Its `BLOCKED` holds the PR. Review `git show <sha>` from your own checkout, never `git -C` into the child's worktree. gitops runs `git cherry-pick <sha>` in the task worktree. When the pick conflicts, gitops runs `git cherry-pick --abort` and reports, and you rerun the unit serially on the new task head, as a foreground `orbit:poteto-agent` in the task worktree. When the unit's row names another provider, each serial rerun in this step is a `delegate_task` on that provider with `isolation: "shared"`, as A cell that names a provider says. Then settle the child with `t3_thread_organize` action `settle`, and run `git worktree list`. You, not gitops, remove a child worktree that remains with `git worktree remove <path>`, and its branch with `git branch -D <branch>` when its tip is the SHA you picked. Never claim that settle removed them. An owner's commits reach its PR branch, so its wake has no cherry-pick, and you keep its worktree for the later rounds.
8. A fix round after the cherry-pick runs as a foreground `Agent` with `orbit:poteto-agent` in the task worktree. When the unit's row names another provider, the round is a `delegate_task` on that provider with `isolation: "shared"`. Only a full redo of the unit is a new `delegate_task`, with a new `clientRequestId`, and it counts as one failed try.
9. `task_cancel` a stuck child before you start its replacement. Told to run fewer, or to go on without a delegate, `task_cancel` the extras and start none. Until its wake arrives, a tick judges a running child only by its trail and its git side effects, and never calls `task_status` on it.
10. An owner's build round is its only child. Each later round, a fix or a rebase, is a foreground `Agent` in your thread with no `isolation`. Its brief names the owner's worktree path and branch and carries step 5's build contract verbatim. The round runs every command there by absolute path and `git -C <path>`. When the owner's row names another provider, each such round is a `delegate_task` on that provider with `isolation: "shared"` and the same brief. When `git worktree list` no longer shows that worktree, the round is a fresh `delegate_task` instead, whose brief runs step 2's guard and then `git switch -C <branch> <head sha>`. When another worktree holds the branch, that child stops and reports, and never forces it. A new round never goes through `t3_thread_send`.
11. A child starts no child thread. Its own units that need their own checkout run one at a time in its worktree.

Never wait on a task whose result carries `next`, as you never poll it. `task_status` reports the task's `workState` as `working`, `waiting_for_children` or `result_available`. A finished turn with live child work is not done, so read the result and settle the child only at `result_available`. T3 holds the wake until the child's own subagents and background work settle, so a wake normally finds `result_available`. When `task_status` shows `working` or `waiting_for_children`, do not read the result, settle the child or poll it. Its wake still comes, and until then step 9 treats it as a running child.
A `task_status` or `task_cancel` call with an id that T3 does not know lists this thread's open delegated tasks. When a compaction lost a child's `taskId`, make that call. Recover the ids only from that list, never by polling.
The reply names a child or any other thread by the `link` its result carries, never by an id or a title.
Stop a child with `task_cancel`, never `t3_thread_interrupt`. Use `t3_thread_organize` action `archive` only for a child you abandon.
When `task_status` or `delegate_task` reports `hasPendingQuestion`, or T3 tells this thread that a child asks a question, call `t3_pending_request` with `threadId` set to the `childThreadId`. Use `list` for the request ids and `read` for the request. Then `respond` with `answers` when the brief's context answers it, else ask the user. The child's completion still brings the wake of step 6. Approvals do not reach `t3_pending_request`. Probe `t3_pending_request` as Probe says before its first call. When it is absent, archive a child that waits on a question.

## Models

`orbit models resolve <task> --json` resolves a role, a work type (`code --work-type <name>`) or a panel, with every Models source merged (rules.md Workflow Defaults, Models). Its `mode` says how the spawn runs. `inherit` omits `model`. `alias` passes `alias` as the model when your subagent tool takes it, else omits it, as Any lead says. `same-provider` runs on your own subagent tool with `target.model`, as A target on your provider says. `delegate` spawns `delegate_task` with `target`, whose `options` already use the model's own option ids, and `candidates` lists a seat's entries in try order. `ask`, `hold`, `skip` and `unavailable` take the paths below and in `t3-seats.md`. A panel (`interrogate`, `arena`) returns one such result per seat in `seats`. Without `orbit` on PATH, resolve each cell by hand from the sources rules.md names.

### Seats on another family

Read `t3-seats.md` in this folder when the `other-family` Models row lists providers, or the `verifier` row's Model is `other-family`, `other-family, inherit` or a target on another provider. Otherwise a seat on another family that a skill names runs the skill's session-family seat, an `Agent` spawn with the model its role resolves. When a skill names such a seat and the `other-family` row is empty or missing, the reply says `No seat on another family is configured. /orbit:setup lists providers.`

Call `orchestrator_capabilities` once per thread, before the first `delegate_task` of any kind, and reuse the result. Call it again only after an error or a user-named provider change, or with `search` for a model the Models table names, as `t3-seats.md` says. It holds `inheritedProviderInstanceId`, `inheritedModel`, the parent's runtime mode and `providers`, in listed order. Each provider has `providerInstanceId`, `driverKind`, `canRunCrossProviderChildTask`, `constraints` and `models`. A provider that offers only some runtime modes also lists them in `runtimeModes`. Each model has an `id` and may list `options`, each an `id` with its `values`. The effort option's `id` differs per provider.

When the row's Effort names a value that one of the model's `options` lists in `values`, pass `target.options` as `[{id, value}]` with that option's `id`. Otherwise pass `options: []`, which clears the inherited options, so the provider default runs.

### A cell that names a provider

A Models cell may hold one target, `<providerInstanceId>/<model>`, split at the first `/`, on any row (rules.md Workflow Defaults, Models). A `, <value> after <n> failed tries` value may be a target too, and it runs this way once it holds. This section overrides every rule in orbit that keeps a spawn native or on the lead's provider, for each spawn whose cell holds a target.

**A target on your provider.** Its `providerInstanceId` equals `inheritedProviderInstanceId`. Run the spawn on your own subagent tool with the target's model part as the model. When your subagent tool takes only short aliases, pass the alias that is a token of the model id. With no alias that matches, omit `model` and say so in the reply. A lead whose own subagent tool cannot take the model sends the spawn to a same-provider `delegate_task` with `target.model` set to it. The reply never claims that the exact version ran. A spawn that fails because its model is unavailable or at its usage limit retries as rules.md Workflow Defaults, Models says, not as **Otherwise** below says.

**A target on another provider.** It runs there only when you lead with `delegate_task` and the provider holds. The provider holds when it is in `providers`, is enabled, has `canRunCrossProviderChildTask` true, lists the model and offers the parent's runtime mode when it lists `runtimeModes`. The first result is a short list, so before you call the model not listed, call `orchestrator_capabilities` with `search` set to the model id. Spawn with `delegate_task` and `target: {providerInstanceId, model, options}`, with `options` from the row's Effort as Seats on another family says.

- A child that shares your checkout, such as the advisor, gitops, a serial delegate or a fix round, gets `isolation: "shared"`, `mode: "async"` and a `clientRequestId` as Where a child runs step 4 says. Follow `next` and wait for the wake, as step 6 says. T3 starts a `shared` child in this thread's bound checkout, else in the project root (Where a child runs step 2). So the brief names your checkout's absolute path, as `git rev-parse --show-toplevel` prints it. The child runs every command there by absolute path and `git -C <path>`, as step 10's brief does. Its first command is `git -C <path> rev-parse --show-toplevel`. When that does not print the path, the child stops and reports.
- A child that needs its own checkout, or runs while you keep working, follows Where a child runs steps 2 to 11 with this target in place of `inheritedProviderInstanceId`.
- The child gets none of this thread's context, so the brief stands alone. It holds the user's goal in one line, orbit's plugin folder as an absolute path, the agent file `agents/<name>.md` with the agent's `tools` limit, and "You are a subagent of this thread. Start no child thread." A `general-purpose` child gets the playbook `SKILL.md` path in place of the agent file, as step 5 says. A child that shares your checkout also gets your checkout's path and its first command, as above. `role` follows step 3.

**Otherwise.** A target on another provider runs as if the cell were empty when you are a child or a subagent, when `delegate_task` is absent, or when the provider fails a check. It then takes the next source or the default. The reply says `<cell> unavailable: <reason>`. The reason names the check that failed or quotes the provider's `constraints`. A target child on another provider that errors, hits a limit or returns nothing reruns once as if the cell were empty. The reply says `<cell> unavailable: <reason>`, and the reason quotes the child's error or names the limit or the empty result. A `verifier` target keeps its own path, below.

**A `verifier` target on another provider.** Each verifier is the verifier seat with that one entry, as `t3-seats.md` says, with no family check. When the entry is unavailable, the verifier takes that file's path for a verifier whose every entry failed, which asks the user or holds the PR. It never runs as if the cell were empty.

## Paths

Paths in this file are relative to orbit's plugin folder, two levels above this file's folder. The installed plugin folder is `~/.config/orbit/current/plugin` when the `orbit` CLI manages the install.
