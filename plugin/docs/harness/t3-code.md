# Orbit in T3 Code

This is orbit's T3 Code adapter, at the path pstack uses for a host adapter. Orbit's skills come from pstack, which uses Cursor names. Orbit already uses Claude Code names, as pstack's Claude Code adapter maps them. This file adds T3 Code. Read it once per session, before the first step that opens or waits on a PR, schedules a wake or routine, asks for a secret, renders a verdict's proof table, fills a panel seat on another family, would start a child thread, runs a browser step the user asked for, or spawns a child in plan mode. Never pass a field or value the tool schema rejects.

## Probe

T3 Code serves its tools as MCP tools named `mcp__t3-code__<name>`, and most of them are deferred. Before calling a T3 tool, check that tool itself. It is present when it is already in your tool list, or when `ToolSearch` with `select:mcp__t3-code__<name>` loads it. With no `ToolSearch`, a tool not in your list is absent. T3 tools may load late. Try a missing tool's name once, by `ToolSearch` `select:` or else by its first real call, before you call it absent. A tool that is not present takes the absent column. Never key on an environment variable, a path, or another tool of the same family, because T3 can turn one tool off and leave the rest. Each subagent checks for itself. A lead on another provider probes as Lead on another provider says.
Under a Codex lead, look for a tool under both `t3-code` and `t3-code-direct` before you call it absent, as Lead on another provider says. A session connected to T3 from outside, such as one added with `claude mcp add t3`, still lists the tools that act as the calling thread, so the list alone does not make them present. When a call returns an error that the tool needs an agent running inside T3 Code, take the absent column for it and for the rest of those tools, which cover subagents, secret requests, rendered HTML, the browser preview, devices and worktree handoff. Never call `t3_thread_launch` in their place unless the user asked for a new thread.

## Where a child runs

Find the row for what the child needs and the column for where you run. The lead is the agent whose turn end returns to the user. T3 otherwise means you are a child or a subagent, or `delegate_task` is absent. In T3, no `Agent` call passes `isolation: "worktree"`.

| Child | T3, lead with `delegate_task` | T3 otherwise | Not T3 |
| --- | --- | --- | --- |
| Shares your checkout, such as a read-only child (the `how` explainer, the advisor, a judge, a verify lane that reads a SHA from an export), gitops, a serial delegate, a fix round or comment-sicko | `Agent` with `run_in_background: false` and no `isolation`. | Same as the lead. | `Agent` with no `isolation`. |
| Needs its own checkout, such as a parallel delegate, an arena runner, an interrogate adversary, a swarm worker that writes, or the native verifier | Same-provider `delegate_task`, as the list below says. | One unit at a time in your own checkout. Never make a checkout in the shell. | `Agent` with `isolation: "worktree"` under Claude Code. Under another lead, its native subagent's worktree option, else one unit at a time in the task worktree. |
| Runs while you keep working, such as an autopilot owner or an orchestrate worker | Same-provider `delegate_task`, as the list below says. | One at a time, as a foreground `Agent` with no `isolation`. The reply says the tick cannot fire while it runs. | `Agent` with `isolation: "worktree"`, rolling under the Parallel cap (rules.md Workflow Defaults). |
| A panel seat, or the verifier seat, on another family | A roster seat, as Seats on another family says. | The session-family seat, as Seats on another family says. | The session-family seat. |

A same-provider child runs this way.

1. Probe `orchestrator_capabilities`, `delegate_task`, `task_status`, `task_cancel` and `t3_thread_organize` as Probe says. Call `orchestrator_capabilities` once per thread, as Seats on another family says.
2. Commit what the child needs on the task branch first. The child's checkout starts from your commit, and T3 does not copy uncommitted edits.
3. Call `delegate_task` with `isolation: "worktree"`, `mode: "async"` and no `runtimeMode`. Set `target.providerInstanceId` to `inheritedProviderInstanceId`. Set `target.model` to that provider's id for the model the spawn's Models role resolves, and omit it for `inherit`. Pass the role's effort in `target.options` as Seats on another family does, else `options: []`. `role` is `implementation` for a writer or an owner, `review` for an adversary and `test` for the verifier. `title` names the skill and the unit.
4. `clientRequestId` is `<skill>-<unit>-<short base sha>-try<n>`. A retry of the same call after a tool error or a lost response reuses it. A new try or round takes a new one.
5. The brief names the plugin folder and the agent file, as A brief to an orbit agent says, and states the agent's `tools` limit. It says "You are a subagent of this thread. Start no child thread." It tells the child to commit its unit by path itself and to report its worktree path from `pwd`, its branch and the commit SHA. An owner's brief also allows native subagents in the foreground.
6. The result carries `next`. Follow it and never poll. Keep working, or end the turn.
7. On the wake, read the result with `task_status`. Review `git show <sha>` from your own checkout, never `git -C` into the child's worktree. gitops runs `git cherry-pick <sha>` in the task worktree. Then settle the child with `t3_thread_organize` action `settle`, and run `git worktree list`. Remove a child worktree that remains with `git worktree remove <path>`, and its branch with `git branch -D <branch>` when its tip is the SHA you picked. Never claim that settle removed them. An owner's commits reach its PR branch, so its wake has no cherry-pick.
8. A fix round after the cherry-pick runs as a foreground `Agent` with `orbit:poteto-agent` in the task worktree. Only a full redo of the unit is a new `delegate_task`, with a new `clientRequestId`, and it counts as one failed try.
9. `task_cancel` a stuck child before you start its replacement. Told to run fewer, or to go on without a delegate, `task_cancel` the extras and start none. A tick judges a running child only by its trail and its git side effects. It never calls `task_status` on a child whose result carries `next`.
10. An owner's later round settles the prior child and confirms with `git worktree list` that no worktree holds the branch. A fresh `delegate_task` then takes the round. Its brief runs `git switch -C <branch> <head sha>` first. When another worktree holds the branch, the child stops and reports, and never forces it. A new round never goes through `t3_thread_send`.
11. A child starts no child thread. Its own units that need their own checkout run one at a time in its worktree.

### Seats on another family

A skill may name a seat on another family, such as arena's cross-judge, interrogate's second adversary, the show-me-your-work trail reviewer or autopilot-full's audit seat. The session-family seat is the seat the skill names, run on the session's own family. It is an `Agent` spawn under a Claude lead and the native subagent under another lead. Fill one such seat per panel. Only the agent whose turn end returns to the user fills a roster seat. A subagent takes the absent column, because its turn end returns to its parent and the child's wake lands on the lead's thread. Seats that write the change's code, such as arena runners, delegates, swarm workers and live lanes, never take a roster seat. They run on the lead's provider, as Where a child runs says.
When the `verifier` row's Model is `other-family`, each verifier that shipping step 1 spawns is such a seat too (`skills/playbook/playbooks/shipping.md`). It fills one seat per PR, not one per panel.

Probe `orchestrator_capabilities`, `delegate_task`, `task_status`, `task_cancel` and `t3_thread_organize` as Probe says. If any is absent, the absent column applies.

Call `orchestrator_capabilities` once per thread, before the first `delegate_task` of any kind, and reuse the result. Call it again only after an error or a user-named provider change, or with `search` for a model the Models table names, as below. It holds `inheritedProviderInstanceId`, `inheritedModel`, the parent's runtime mode and `providers`, in listed order. Each provider has `providerInstanceId`, `driverKind`, `canRunCrossProviderChildTask`, `constraints` and `models`. A provider that offers only some runtime modes also lists them in `runtimeModes`. Each model has an `id` and may list `options`, each an `id` with its `values`. The effort option's `id` differs per provider.

The session's family is the `driverKind` of the provider whose `providerInstanceId` equals `inheritedProviderInstanceId`. The roster is every provider, in listed order, with `canRunCrossProviderChildTask` true, a non-empty `models` list and a `driverKind` other than the session's family. Never put the session's own provider on the roster. When no provider's `providerInstanceId` equals `inheritedProviderInstanceId`, say so in the reply and use the session-family seat.

The `other-family` row of the Models table picks the seat, with each cell resolved as rules.md Workflow Defaults, Models says. A provider's first eligible model is its first listed model whose `id` does not start with the first word of `inheritedModel`, its text before the first `-`. That skips a model of the session's own family that another provider hosts. A model whose `id` is `auto` or `default` stays eligible, and the reply names it. An empty Model cell or no row takes the first roster provider with an eligible model, and its first eligible model. `inherit` keeps the session-family seat. Otherwise the Model cell is an ordered list of entries. The list tries only values from a family other than the parent's, in list order, so skip an entry whose provider is of the session's family. A bare `<providerInstanceId>` takes that provider's first eligible model, and holds when that provider is on the roster and has one. `<providerInstanceId>/<model>` is an explicit pick, split at the first `/` because a model id can hold one. It holds when that provider is on the roster and lists that model. The first result is a short list, so before you call a pick unavailable because its model is not listed, call `orchestrator_capabilities` with `search` set to the model id. An entry that does not hold puts `<entry> unavailable: <reason>` in the reply, and the next entry is tried. The reason quotes the provider's `constraints` verbatim or names the check that failed. A seat that runs commands, such as interrogate's roster adversary, skips a provider whose listed `runtimeModes` lacks the parent's runtime mode. That provider steps the child down to a narrower mode, which can ask for approval on commands and stall on the user, so it is `<entry> unavailable: runtime mode <mode> not offered`, and the next entry or roster provider is tried. When no entry holds, use the session-family seat. Never fill the seat from a provider the list does not name, and never replace an entry without saying so.
The verifier seat runs commands too, so it skips such a provider the same way.

When the row's Effort names a value that one of the model's `options` lists in `values`, pass `target.options` as `[{id, value}]` with that option's `id`. Otherwise pass `options: []`, which clears the inherited options, so the provider default runs.

Spawn the seat with `delegate_task`, `target: {providerInstanceId, model, options}`, `role: "review"`, `mode: "async"`, a `title` naming the skill and the seat, a `clientRequestId` naming the skill, the seat and the round, and no `runtimeMode`. A retry of the same call after a tool error or a lost response reuses that `clientRequestId`, so T3 returns the same child and starts no second one. A new round and a fallback to the next entry each take a new one. A new round's brief carries the original brief, the prior round's findings, the responses to them and the objections still open. A seat that only reads keeps the default `isolation`. Interrogate's adversary runs repros, so its skill gives it a worktree and its own brief line. A child on another provider gets none of this thread's context, so the brief stands alone. It holds the user's goal in one line, the absolute path of each file to read, the seat's prompt, and "You are a subagent of this thread. Do not edit any file. Return your findings as text." That first sentence keeps a child that loads orbit's rules from acting as a lead. It never holds a secret.
The verifier seat is the second seat that runs code, so like interrogate's adversary it gets `isolation: "worktree"` and its own brief line. In place of the no-edit line, its brief states the verifier's `tools` limit and asks for the first line `BLOCKED: <reason>`, not FAIL, when the change cannot run in that environment. On `BLOCKED`, try the next entry, then the session-family seat, which is the native verifier.
A follow-up that needs the same child's conversation goes through `t3_thread_send` on its `childThreadId`, and a new round is a new `delegate_task` call, per rules.md's Fresh subagents.

Start the panel's other seats too, then end the turn or keep working. The child's completion wakes you. When a `delegate_task` result carries `next`, follow it and do not poll. `t3_background_wait` does not take a `delegate_task` id. When `task_status` or `delegate_task` reports `hasPendingQuestion`, or T3 tells this thread that a child asks a question, call `t3_pending_request` with `threadId` set to the `childThreadId`. Use `list` for the request ids and `read` for the request. Then `respond` with `answers` when the brief's context answers it, else ask the user. The child's completion still wakes you. Approvals do not reach `t3_pending_request`. Read the result with `task_status`. Then check `git status --short` for edits, and settle the child thread with `t3_thread_organize` action `settle`, with `threadId` set to the `childThreadId` that `delegate_task` returned. Use action `archive` only for a child you abandon. Probe `t3_pending_request` as Probe says before its first call. When it is absent, archive a child that waits on a question.
Never wait on a task whose result carries `next`, as you never poll it. `task_status` reports the task's `workState` as `working`, `waiting_for_children` or `result_available`. A finished turn with live child work is not done, so read the result and settle the child only at `result_available`.

When the child errors, hits a limit or returns nothing, try the next list entry, or with no list the next roster provider, then the session-family seat, and say which ran. When the roster is empty, or every list entry or roster seat failed, use the session-family seat and say in the reply that the panel lacked a second family. That line never goes in a trail's Attention header. The reply names each seat's provider and model.
The reply names a child or any other thread by the `link` its result carries, never by an id or a title.
