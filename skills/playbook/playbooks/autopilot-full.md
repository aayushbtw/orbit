### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-id rule in step 3 of `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI. Under Land `main`, a PR here means the item's task branch, its merge is gitops pushing `HEAD:main` per the Land `main` paragraph of `playbooks/shipping.md`, and the Check run there stands in for green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** GitHub CLI (`gh`) is the forge. Each owner is an `Agent` call with `subagent_type: "general-purpose"`, `model: "opus"` and `isolation: "worktree"` that builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, babysits to green per `playbooks/babysit.md`, and merges once steps 4 and 5 clear it. Its brief holds the queue item, its base (`origin/main`), the absolute paths of `SKILL.md` and `../../rules.md`, the grant, the babysit loop in `drive` mode, its trail path and the rule to stop at merge-ready. It runs `/orbit:start <item>` with the Skill tool and returns at merge-ready. Under Land `pr` that is a ready PR the babysit watcher reports `READY`. Under Land `main` no PR opens, so it is a task branch the owner has proven, unpushed. Its report gives the head SHA, the patch-id, the PR link under Land `pr`, the worktree path and branch, and the receipts of its proof. A role such as a PR owner outlives its agent. Once that agent returns, a fresh agent takes the role's next round with the same `Agent` settings minus `isolation`, briefed with the original brief, every later directive, and the prior report, worktree path and branch. Never message an owner that returned.

   The code is ready only after Opening a PR's `/orbit:deslop` and `/orbit:no-comments` passes, so the full swarm runs on finished code. Fix rounds stay on the merge-ready base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the merge-ready report and before a later push that needs a verifier.

   Assume the owner dies. Soon after starting, start a decision trail as `<item>.tsv` in the root's store (`$TMPDIR/orbit-autopilot/<slug>/`, path in your brief) per `../show-me-your-work/SKILL.md`, with your worktree path and branch in its first row. Then commit each finished unit before you start the next. Whoever spawns a subagent records its id, state, and a stuck-after runtime from past runs of its kind in that store's `agents.tsv`, so the root can probe it if the parent dies. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Swarm-verify once.** A full swarm runs once, at the merge-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, and a wording-only change gets none. Fan out independent verifiers at the reported SHA per `/orbit:swarm`, each briefed as step 1 of `playbooks/shipping.md` briefs a verifier, with the worktree path from the report and the Check line. They re-run the Check line, prove the load-bearing behavior live on the real surface through the project's `verify-*` skill or a named driver, and audit the diff. Under Land `pr`, gitops posts your verdict line on the PR per that step. The verdict is not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, doesn't block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. On a verified head, spawn a fresh owner for the merge round, briefed also with the verified SHA, its patch-id and the verdict. Under your verdict and the rules below, it runs only steps 3 and 4 of `playbooks/shipping.md`: the patch-id check, the merge and the read-back. The full playbook would spawn a second verifier. Under Land `main`, it follows the Land `main` paragraph of `playbooks/shipping.md` from the rebase on, ending with gitops pushing `HEAD:main`. Merge prep rebases onto current trunk and waits for green CI. When the patch-id check calls for a fresh verifier, the owner reports the new head and stops, and step 4 verifies it.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, arm `/loop 1h` to audit until no delegated work is left, because long runs drift and agents stall silently. Each tick re-reads this playbook and fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it, because drift is a gap in the record, not a stall. It probes every agent, down to each owner's subagents, and judges each by its side effects, such as trail rows, commits and pushes, because status text and summaries can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an owner that has neither committed nor written a trail row by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once, without waiting for its stop to land. A tick that changed something for the operator ends by telling them what changed in plain words, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR and the trails.
